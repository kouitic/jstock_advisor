## 1. このシステムは何をするものか

jstock_advisor は、**日本株(REIT・ETFは対象外)を、配当と株主優待を重視して
長期保有する個人投資家**のための、判断材料づくりを手伝うツールです。

### やってくれること

- 保有銘柄・気になる銘柄(ウォッチリスト)の情報を毎日自動でチェックする
- 「そろそろ買い時では」「そろそろ利益確定を考えては」「投資した前提が崩れていないか
  確認しては」といった**気づきをLINEに通知する**
- なぜその判定を出したのか、根拠(価格・配当・業績など)を通知に添える
- 過去の判定が実際どうだったか(当たっていたか)を後から自動で振り返る
- 判定のルール(しきい値)を変えたいときは、変更内容を記録し、利用者本人が
  承認するまでは実際の判定に反映されない仕組みを用意する

### やってくれないこと(重要)

- **自動売買はしません。** 実際に株を売買するのは、常に利用者本人がご自身の
  証券会社の取引画面などで行う必要があります。このシステムは「買った・売った」という
  実績を後から記録することはできますが、注文を発注する機能はありません。
- **全上場銘柄を毎日スキャンするわけではありません。** 自動で調べるのは、
  利用者が「保有銘柄」または「ウォッチリスト」として登録した銘柄だけです
  (詳しくは4節)。
- **「絶対に儲かる」ことを保証するものではありません。** 判定はあくまで、
  取得できたデータに基づく機械的な計算結果です。判断材料の一つとして
  利用してください。
- 判定に必要なデータが取得できない場合、システムは**推測で埋め合わせることを
  しません**。「データ不足」「算出不可」とはっきり表示します。これはこのシステム
  全体を貫く設計方針です。

## 2. 全体の流れ

```
① 事前準備          ② 毎日の自動処理              ③ 利用者への通知      ④ 利用者の行動
──────────         ────────────────────         ──────────────      ──────────────
保有銘柄・            決まった時刻に自動起動          LINEにメッセージが     通知を見て、必要なら
ウォッチリスト・       ↓                             届く                  証券会社で実際に売買
株主優待などを         インターネット上の株価・        (「買い候補」            ↓
最初に登録            決算・配当データを取得           「利確検討」            実際に売買したら
(利用者が手動で登録)   ↓                             「至急確認」など)        CLIやLINEチャットで
                     Pythonのプログラムが            ↓                     記録
                     判定を計算                    根拠(価格・理由・
                     ↓                             信頼度)も一緒に表示
                     前回と同じ内容なら
                     通知を送らない(重複防止)
```

いったんAWS(Amazonのクラウドサービス)にセットアップを済ませてしまえば、
**利用者のパソコンを起動しっぱなしにする必要はありません。** ②の自動処理は
すべてクラウド上のスケジュールで動くため、あとはLINEの通知を待つだけです
(詳しくは9節)。

## 3. 事前に登録が必要なデータ

自動で取得できないデータは、利用開始前に利用者自身が登録する必要があります。

| 登録するデータ | 内容 | 自動取得の可否 |
|---|---|---|
| 保有銘柄 | 銘柄コード・株数・購入価格・購入日・口座区分(NISA/特定/一般) | 不可(初回登録が必須) |
| ウォッチリスト | 気になっている銘柄のコード、優先度、目標株価など | 不可(登録した銘柄のみ監視対象) |
| 株主優待 | 優待の内容・必要株数・優待価値の見積もりなど | **不可(必ず手動登録)** |

株主優待だけは特に注意が必要です。株価や決算データと違って、株主優待の内容を
自動で取得できる公式なデータ源が存在しないため、**優待がある銘柄は必ず利用者が
会社発表などの一次情報を確認したうえで登録**してください。未登録のままだと、
その銘柄の「配当+優待をあわせた利回り」の計算や、「優待が廃止された」という
検知が働きません。

### 3.1 保有株数×保有期間で内容が変わる優待への対応

企業によっては、優待の内容が「何株持っているか」だけでなく「何年継続して
保有しているか」によっても変わります(例: 100株を6ヶ月以上持っていれば
500円分、同じ100株でも2年以上持っていれば1,000円分、1,000株を4年以上持って
いれば20,000円分、といった具合)。このシステムは、この2つの軸の組み合わせ
(マトリクス)を登録できるようになっており、実際にどの区分に該当するかは、
**保有銘柄データに登録されている「最初に購入した日」を起点に、実際の保有
株数と保有期間の両方を満たす中で最も条件の良い区分を自動的に1つだけ選び**
ます(複数の区分の金額を誤って合算してしまうことはありません)。

「2年以上3年未満」のように保有期間に上限がある優待も登録できます。上限を
設定しない場合、その条件を一度満たした保有者は期間の上限なく該当し続ける
扱いになります。

### 3.2 権利確定日の自動計算

「毎年3月末」のように優待の権利が確定する月だけが分かっている場合、
このシステムはその月の**実際のカレンダー上の月末日**(2月なら28日か29日、
30日までの月・31日までの月をそれぞれ正しく判定)から、次にやってくる
権利確定日を自動的に計算し、保持します。日付が過ぎればその都度、次の年の
同じ月へ自動的に繰り越されるため、日付を都度手入力し直す必要はありません。

## 4. 自動でチェックしてくれる範囲

| 対象 | チェックする内容 | 補足 |
|---|---|---|
| 保有銘柄(全件) | 利益確定を検討すべきか/投資した前提が崩れていないか/買い増し候補になるか(2026-07-31改訂。5.6節) | 登録した保有銘柄はすべて毎日チェック対象 |
| ウォッチリスト(全件) | そろそろ買い時か | 登録した銘柄はすべて毎日チェック対象 |
| 買い候補の新規発掘 | ウォッチリスト登録銘柄・保有銘柄の中から買い候補(新規購入・買い増し)を探す(2026-07-31改訂: 従来はウォッチリストのみが対象でしたが、保有銘柄も同じ基準で買い増し候補として評価するようにしました。5.6節) | **市場全体の自動スクリーニングではありません。** 現時点では市場全体をスキャンできる無料のデータ源が接続されていないため、ウォッチリスト・保有銘柄に登録した銘柄の中からのみ探します |

## 5. 買い時の判定(買い候補・ウォッチリストの買いシグナル)

**最も重要な原則(2026-07改訂)**: 「企業として投資候補になり得るか」と
「現在の株価で実際に購入すべきか」を明確に分けて判定します。どれだけ良い企業でも、
現在の株価が高すぎれば「購入候補」にはせず「価格待ち」として扱います。逆に、
相対的に順位が高いというだけの理由で、価格条件を満たさない銘柄を購入候補として
通知することはありません。

### 5.1 3段階の判定手順

1. **第1段階: 投資対象スクリーニング** — 配当+優待の合計利回りが低すぎる、
   出来高が少なすぎて売買しにくい、財務が弱すぎる(債務超過等)、継続企業の
   前提に疑義がある、直近決算で業績が大きく悪化している、直近の公式発表に
   重大なリスクキーワードが含まれる、データが古すぎる、といった銘柄はここで
   「対象外」として除外されます。
2. **第2段階: 企業魅力度の評価(company_quality_score)** — 足切りを通過した
   銘柄について、「総合利回りの魅力度」「配当の安定性」「財務健全性」
   「割安度」「株主優待の価値」「業績の安定性」「株価の安定性」という複数の
   観点から100点満点で採点します。これは「良い企業かどうか」の評価であり、
   この時点では現在の株価で買うべきかどうかは決めません。割安度の観点は、
   PER/PBR倍率・配当利回り・適正価格対比・株価下落(財務悪化以外の理由に
   限る)という4つのカテゴリに分けて上限点を設定しており、値下がりしている
   ことだけを理由に高得点を与えないようにしています。
3. **第3段階: 現在価格での購入判断(BuyAction)** — 現在の株価と、適正価格の
   信頼度・手法間のばらつき・決算発表までの日数等に応じて動的に決まる
   「打診買い/標準買い/積極買い」の3段階の目安価格とを比較し、以下のいずれかに
   判定します。
   - **積極購入候補 / 購入候補 / 打診購入候補**: 現在値が目安買い価格の
     いずれかを満たしている(価格条件は必須で、企業魅力度スコアだけで
     この3区分へ昇格することはありません)
   - **監視継続(価格待ち)**: 企業として魅力はあるが、現在値が打診買い価格を
     上回っている(値下がりを待つ)
   - **監視継続(決算待ち)**: 次回決算発表が3営業日以内に迫っている
     (ローリスク・長期保有方針のため、決算直前の新規購入は原則として待ちます)
   - **要確認**: 判定内容に矛盾が検出された、または適正価格算出手法間の
     ばらつきが大きすぎる場合
   - **購入見送り**: 企業魅力度スコアが基準を大きく下回る

### 5.2 目安買い価格の決め方(固定比率方式を廃止)

以前は、適正価格に対して一律95%/90%/85%を掛けた3価格を「打診買い/標準買い/
積極買い」としていました。2026-07の改訂でこの方式を廃止し、以下のように
銘柄ごとの状況に応じて必要な安全余裕率を動的に決定するようにしました。

- 適正価格は単一の断定値ではなく、複数の算出方式(目標配当利回り・PER・PBR・
  過去株価レンジ・簡易DCF・業種別方式)の結果を集約した「レンジ」として扱い、
  そこから保守的に「購入判断基準価格」を1つ算出します。手法間のばらつきが
  大きい銘柄ほど、より保守的な基準価格になります。**現在値の10%未満、他方式
  中央値の40%未満・250%超、52週安値の50%未満といった極端な算出値は、算出
  誤差または前提の異常による外れ値とみなして集計から除外します**(2026-07-31
  改訂。簡易DCFが単年度キャッシュフローの歪みで異常に低い値を出すケースを、
  実際の運用で確認したため)。除外前の全手法参考値と、除外後の実際に判断へ
  使った値のレンジは別々に記録し、通知には除外後のレンジのみを表示します。
- 必要な安全余裕率は、適正価格の信頼度(高い/中程度)を基本とし、以下のような
  リスク要因がある場合に加算されます: 決算発表が近い、算出手法間のばらつきが
  大きい、業種別の専用評価モデルが未整備、市況の影響を受けやすい業種、
  時価総額が小さい・出来高が少ない、業績のブレが大きい、一時的な利益の
  上振れが疑われる、主要顧客への依存度が高い、データ品質に懸念がある。
  **これらのリスク要因は「適正価格のばらつき系」「業種・事業系」「業績品質系」
  「決算タイミング系」「データ品質系」「流動性系」の6カテゴリに分類し、
  同一カテゴリ内で複数該当しても最大値のみを採用します**(2026-07-31改訂。
  例えば自動車部品業種では「業種別モデル未適用」「市況の影響を受けやすい」
  「主要顧客への依存度が高い」がほぼ常に同時発生し、これらを単純合算すると
  実質的に同じリスクを何重にも加算してしまっていたための修正)。また、
  打診買い・標準買い・積極買いの3段階には同じ加算額をそのまま使わず、
  段階が進むほど強く反映する仕組みにし、3段階それぞれに個別の上限を設定
  しました。これにより、リスク加算が大きい銘柄でも3段階の買付価格が
  すべて同額になってしまうことを防いでいます。安全余裕率の全体上限は
  45%です。
- 適正価格の信頼度が低い場合は、自動での目安買い価格の算出自体を行いません
  (推測で価格を出さず、「監視継続」または「要確認」とします)。
- **買付価格の信頼性チェック(2026-07-31追加)**: 必要安全余裕率が打診買いの
  上限を超えてしまう場合や、手法間のばらつきが大きい・有効な算出方式が
  少ない・データ品質に懸念がある等の項目が複数該当する場合は、機械的に
  算出した目安買い価格をそのまま購入候補の判定に使わず、「監視継続」または
  「要確認」として扱います(無理に低い買付価格を提示しません)。

### 5.3 平準化EPS(景気循環銘柄向け)

鶏卵・自動車部品・素材等、市況の影響を受けやすい業種の銘柄では、単年度の
予想利益だけでPER方式の適正価格を算出すると、一時的な市況要因による増益を
過大評価してしまう可能性があります。該当業種では、予想EPSと過去5年の黒字年度
中央値のうち低い方を採用する「平準化EPS」を使用します。

### 5.4 LINE通知の対象(2026-07-31改訂: 購入候補のみに一本化)

**LINE通知するのは、現在の株価で実際に購入条件を満たした銘柄(積極購入候補/
購入候補/打診購入候補)だけです。** 監視継続(価格待ち・決算待ち)・購入見送り・
要確認・データ不足は、分析結果と判定理由をすべて記録しますが、LINEへは
通知しません(以前は監視継続銘柄もLINE通知していましたが、「今日買った方が
よい銘柄だけを知りたい」というご要望に合わせて廃止しました)。

購入候補は優先順位(企業魅力度スコアが基準を満たしたうえで、現在価格が
どれだけ有利かを示す購入魅力度スコアが高い順)に並べ、1回の実行で最大5銘柄
(件数は`config/notification_rules.yaml`で変更可能)を1通のLINEメッセージに
まとめて通知します。「相対順位が高い」という理由だけで購入候補として通知する
ことはなく、現在価格で条件を満たす銘柄が1件もない日は、原則としてLINE通知
自体を送りません(運用確認のため完了通知が必要な場合は設定で有効化できます)。

順位が高い銘柄でも、直近の再通知抑止(前回通知からの経過日数・価格変動が
小さい)やデータ品質の懸念により送信対象から外れることがあります。その場合、
単に送信件数が減るのではなく、次点以降の順位の銘柄を繰り上げて評価し、
条件を満たす銘柄が続く限り最大件数まで埋めます(2026-07-31改訂: 以前は
上位5件を先に確定してから送信可否を判定していたため、上位に抑止対象が
含まれると実際の送信件数が5件を下回ることがありました)。なお、購入候補の
データ品質に懸念がある場合でも、保有銘柄の売却判定で使われる「要手動確認」
LINE通知は送信されません(懸念自体は監査ログに記録されたうえで、その銘柄
だけが静かに送信対象から外れます)。

個別銘柄の株価データ取得に失敗した場合も、既定ではLINE通知しません
(CloudWatchログと完了サマリーの件数内訳にのみ記録します)。

### 5.5 買い候補として通知される内容

- 順位、銘柄コード、銘柄名、判定区分(積極購入候補/購入候補/打診購入候補)
- 現在の株価、適正価格レンジ(外れ値除外後)、購入判断基準価格
- 3段階の目安買い価格(打診買い/標準買い/積極買い)、現在値がどの価格条件を
  満たしたか
- 企業魅力度スコア、購入魅力度スコア(現在の株価が買い時にどれだけ近いかの目安)
- 予想配当利回り、株主優待利回り、合計利回り
- 主な評価理由(企業魅力度)、主なリスク
- 次回決算日(評価日より過去の日付は「不明」として扱います。データ提供元の
  更新遅延で過去日が返ってくることがあるため、2026-07-31改訂)
- 配当・優待の権利確定日(わからない場合はその理由も表示。2026-07-31改訂で、
  「会社公式情報」「手動登録データ」「データ提供元」「決算期末等からの推定」
  「情報なし」のどれに基づく日付かも情報区分として表示するようにした)
- 適正価格の信頼度

算出手法間のばらつき・業種別モデルの適用有無・全手法参考値・必要安全余裕率を
拡大した理由等の詳細情報は監査ログに記録され、通知本文には表示しません。

### 5.6 保有銘柄の買い増し候補について(2026-07-31改訂)

以前は、買い候補の探索対象はウォッチリストの銘柄だけで、保有銘柄はもっぱら
6節の「利確・売却」の判定対象でした。この改訂により、**保有銘柄についても、
気になる銘柄と全く同じ購入判断ロジック(5.1〜5.3節)で「今、買い増しすべきか」を
評価する**ようになりました。同じ銘柄が気になる銘柄・保有銘柄の両方に登録されて
いる場合、判定は1回だけ行われ、通知にも二重に出てくることはありません。

**最も重要な原則**: 「その銘柄をすでに持っているから買う/買わない」という
判定は、いかなる場合も行いません。保有していることや、平均取得単価が
いくらだったかは、通常の購入判断(適正価格や目安買い価格の計算)には
一切使いません。含み損が出ている銘柄を、損を取り戻すために機械的に
「ナンピン買い」候補として勧めることもありません。あくまで、気になる銘柄と
同じ基準で「今の株価が魅力的かどうか」だけを判定します。

保有銘柄については、通常の購入判断に加えて、次の買い増し特有のリスクも
確認し、いずれかに該当すると買い増し候補としての通知は送りません
(通常の購入判断自体は変わらず記録・監査されます)。

- **売却・利益確定の判定との矛盾**: 同じ銘柄について、6節の売却・利確判定が
  「売却を検討」「至急確認」などの売り時シグナルを出している場合、買い増しの
  通知はしません(買いと売りのシグナルが同時に出ることを防ぎます)。
- **保有データの矛盾**: 株数や平均取得単価が0以下になっている等、データとして
  明らかにおかしい場合は買い増し候補にしません(単元未満株を持っていることは
  それだけでは異常とは扱いません)。
- **銘柄集中度・業種集中度**: その銘柄を買い増した場合に、ポートフォリオ全体
  (時価総額ベース)に占める比率が基準(初期値20%)を超える、または同じ業種の
  合計比率が基準(初期値35%)を超える場合は買い増し候補にしません。**保有銘柄
  全員分の時価総額が正確に把握できていない日は、比率を「算出不可」として扱い、
  安全側に倒して買い増し候補の通知自体を送りません**(時価総額ベースと
  取得価格ベースの数字を混ぜて計算することはしません)。

買い増しの株数は、常に**最低売買単位(1単元)だけを買い増した場合**を
仮定して計算します。手元の資金にどれだけ余裕があるかを把握するデータが
無いため、それ以上の株数や金額を「これだけ買い増すとよい」という形では
提案しません。

気になる銘柄・保有銘柄の買い候補は、優先順位付けも通知の上限件数(最大5件、
5.4節)もまとめて1本のリストとして扱われます。保有銘柄だからといって
優先されたり、逆に後回しにされたりすることはありません。通知には、
保有銘柄であることが分かるよう、保有株数・平均取得単価・含み損益(参考情報。
購入判断の根拠には使っていません)が追加で表示されます。

### 5.7 ウォッチリストへの自動追加(週次スクリーニング、2026-08-01追加・2026-08-01候補ユニバース本格対応)

これまで「気になる銘柄(ウォッチリスト)」への登録は、すべて手動(CLIまたは
LINEチャット)で行う必要がありました。この機能により、**東証プライム市場+
スタンダード市場の全上場銘柄(約3,122銘柄、2026-07時点)**の中から、高配当・
財務健全性の条件を満たす銘柄を**毎週土曜07:00に自動でウォッチリストへ
追加**するようになりました。追加された銘柄は、翌営業日(月曜08:00)の
買い候補分析にそのまま組み込まれます(5節の判定ロジック自体は一切変更して
いません)。

**候補銘柄の一覧について(2026-08-01改訂)**: 当初は利用者があらかじめ
用意したCSVファイルに載っている銘柄だけが評価対象でしたが、東証(日本取引所
グループ)が毎月公開している上場銘柄一覧を毎週自動取得するように変更し、
プライム市場・スタンダード市場に上場している銘柄をすべて自動で候補に含める
ようにしました。市場区分(プライム/スタンダード/グロース)は取得したデータから
判別できるようになったため、15節に記載していた「市場区分の判定ができない」
という制約はこの改訂で解消しています(グロース市場・外国株・優先株は対象外、
上場廃止予定・監理銘柄/整理銘柄の判定はできないため引き続き対象外にできません)。
あわせて、日本経済新聞社が公開しているJPX日経400構成銘柄の一覧も取得し、
追加された銘柄が構成銘柄に該当するかどうかを内部記録・監査ログに残す
ようにしましたが、**この情報は追加の合否判定には使っていません**(あくまで
参考情報)。取得元データの更新が長期間止まっている場合(45日/90日を超えて
更新されない場合)は、安全のためその週の処理を中止し、次回配信を待ちます。
候補範囲を限定したいテスト・段階的な移行のための内部設定(評価対象件数の
上限、市場区分の絞り込み)も用意していますが、通常運用では無効(=全件対象)
です。

**判定条件**(いずれも`config/watchlist_screening_rules.yaml`で調整可能):

必須条件(1つでも満たさなければ対象外):
- 時価総額が一定額(初期値500億円)以上
- 営業キャッシュフローがプラス
- 重大な減配・無配転落の発表がない
- 債務超過・赤字・継続企業の前提への重大な疑義がない
- ETF・REIT(判定精度には既知の制約あり)ではない

スコア条件(配当利回り・自己資本比率・配当性向の健全さ・連続増配年数・
株主優待の有無を配点化し、合計が一定点数(初期値60点/100点満点)以上で合格):
合格した銘柄はスコアの高い順に並べ、**1回の実行につき最大20件まで**を
ウォッチリストへ追加します(件数が多すぎて通知が読みにくくなること・
ウォッチリストが際限なく膨れ上がることを防ぐため)。上限を超えた銘柄は、
翌週以降に改めて評価対象になります。

**追加された銘柄がある場合のみ**、その週の実行結果をLINEへ通知します
(0件の週は通知しません、2026-08-02改訂)。通知には以下が表示されます。

- 対象銘柄数・評価可能銘柄数・データ未検出銘柄数・追加銘柄数・追加率
  (評価可能銘柄数は、実際にスコア計算まで完了した銘柄の数です。データ
  取得エラー・データ未検出だった銘柄は含みません)
- その週の評価ポリシーの条件(配当利回り・自己資本比率等の具体的な基準値)。
  設定ファイルの値をそのまま表示するため、基準を変更すれば通知の表示も
  自動的に追随します
- 追加銘柄ごとの、日本語の会社名(英語表記ではなく)・総合スコア・
  「評価可能◯◯銘柄中△位」という順位・スコアが高かった評価項目とその
  実測値(固定文ではなく、実際のスコア内訳から動的に生成します)

会社名は、東証(JPX)の公式な上場銘柄一覧を最優先で使用します。手動で
個別に登録した表記(まれに必要な場合のみ)、既存のウォッチリスト登録名を
その次に参照し、いずれでも解決できない場合のみ最終手段として証券会社
データ提供元の英語表記等を使用します。すべての情報源で名称が確認できない
場合は証券コードをそのまま表示します(その場合でもウォッチリストへの
追加・通知自体は正常に行われます)。

自動で追加された銘柄は、ウォッチリスト上で「登録元: 自動スクリーニング」
として区別されます。手動で登録した銘柄の内容が自動追加によって上書きされる
ことはありません。また、すでに保有している銘柄・すでにウォッチリストに
登録済みの銘柄は、重複して追加されません。

**約3,000銘柄を評価する仕組み(2026-08-01改訂)**: 全銘柄をまとめて処理するのではなく、
銘柄ごとに独立した処理単位(待ち行列)へ振り分け、複数の処理単位が同時並行で
評価を進める方式に変更しました。これにより件数の上限そのものは撤廃しています
(旧仕様にあった「評価対象件数が300件を超えると処理しない」という制約は
廃止しました)。1銘柄ごとの評価には30〜45秒程度かかるため、約3,000銘柄
全体の処理には数時間規模の時間がかかります。

**処理が長時間終わらない場合の安全策**: 毎時、処理状況を確認する仕組みが
動作しており、処理開始から24時間以内に完了しなかった週次バッチは、そこで
処理を打ち切ります。打ち切った時点までに評価が終わっていた銘柄の結果は
内部記録・監査ログにのみ残し、**ウォッチリストへの追加・LINE通知は行いません**
(全銘柄の評価が終わっていない状態で作った順位表は、実際の実力順とは
限らないため)。この場合は次回(翌週)の実行で最初からやり直します。

**データ取得元(Yahoo Finance)へのアクセスが集中しすぎたと判断した場合の
安全策**: 1銘柄ごとの評価では複数の外部データ取得を行うため、アクセスが
集中しすぎると判断された(「しばらく待ってください」という応答が増えた)
場合は自動的に間隔をあけて再試行しますが、それでも一定割合(初期値20%)を
超えて頻発した週は、取得できたデータの信頼性が下がっている可能性があるため、
その週はウォッチリストへの追加・LINE通知を見送ります(内部記録・監査ログには
残ります)。

**全銘柄の評価完了を検知する仕組みの内部的な頑健性向上(2026-08-07改訂)**:
約3,000銘柄を複数の処理単位で同時並行評価する都合上、「全銘柄の評価が
揃った」ことを検知する内部処理と、個々の銘柄の評価完了を記録する内部処理が
ごく短い時間差でほぼ同時に実行されることがあり、まれにデータベース内部の
一時的な競合が発生して該当の処理単位だけがエラー終了することがありました
(実際に本番運用で1回発生を確認)。この場合も、その銘柄の評価結果自体は
既に保存済みのため失われず、自動的な再送により数分以内に処理が完了して
いましたが、このエラーは想定内の一時的な競合として扱われていなかったため、
不要な再試行が発生していました。この一時的な競合を正常な処理の一部として
扱うよう修正し、無駄な再試行が発生しないようにしました(追加・通知の判定
基準やスコア計算方式は変更していません)。

### 5.8 買い候補の裾野拡大・投資タイプ分類・NEAR BUY監視(2026-08改訂)

これまでの判定は「誤った候補を見せない」ことを重視するあまり保守的になりすぎ、
実際に通知される買い候補が少なくなりすぎていました。この改訂では、**判定の
質そのものは落とさずに**、対象を広げる・接近中の銘柄も継続して知らせる・
通知本文を簡潔にして量を増やせるようにする、という3つの見直しを行いました。

**一次スクリーニングの再整理**: 「総合利回り(配当+優待)が3.5%未満」を理由に
全銘柄を一律除外していたハードゲートを廃止しました。同様に、配当性向・
自己資本比率・営業キャッシュフロー・単年度赤字・直近減配についても、
これまでは1つでも該当すると即座に対象外にしていましたが、**投資スタイル
(下記5タイプ)によって許容度が異なる**ため、一律の除外条件からは外し、
「留意事項」として記録したうえで後続の評価は継続するようにしました。ただし、
**債務超過・継続企業の前提への重大な疑義・重大な不祥事や上場維持リスクの
発覚・出来高不足・データの古さ**という、企業として投資対象になり得るかを
揺るがす重大な項目は、引き続き無条件で対象外とします(緩和していません)。
銀行・証券・保険等の金融業種は、財務指標の意味が通常の事業会社と異なるため、
今回も除外方針を維持しています。

**投資タイプの5分類**: 銘柄ごとに「高配当」「成長株」「割安株」「連続増配株」
「優良株」のどれに当てはまるかを、閾値に基づき機械的に判定し、複数タイプに
同時に当てはまることも許容します(既存の「景気敏感株」等8分類の枠組みを
そのまま拡張したもので、既存分類は変更していません)。成長株・割安株は、
以前は配当利回りの条件も必須でしたが、「配当が少ない/多いことと成長性・
割安度は別問題」という考え方に基づき、配当条件を外して本来の指標
(成長株=営業利益の増加トレンド、割安株=PBR・PERの現在水準)のみで
独立に判定するようにしました。連続増配株は連続増配年数を主な条件とし、
一時的に増配率が小さいだけで対象から外れすぎないようにしています(ただし
今期の会社予想配当が前期実績を下回る=減配見込みの場合は対象にしません)。

**NEAR BUY(買い水準への接近)の継続監視**: 企業として一定の魅力度がありながら
現在値が打診買い価格をわずかに上回っている銘柄(目安: 打診買い価格まで
10%以内に接近、12%を超えたら終了という2段階のゆとりを持たせて頻繁な
出入りを防止)を「NEAR BUY」として継続的に見守り、**条件を満たす限り原則
毎営業日通知**します(通常の買い候補が数日おきの再通知に留まるのとは
異なる特別な通知ポリシーです)。何営業日連続で接近が続いているかも記録し、
その後実際に打診買い等の水準へ到達した場合は「○営業日監視後に到達」と
表示します。一時的なデータ取得エラーで1日だけ確認できなかった場合は
監視自体を打ち切らず、次に確認できた日に継続しますが、表示上の連続日数は
安全側にいったんリセットします(実態と異なる「○日連続」を見せないため)。
1日に通知するNEAR BUY件数には上限(既定5件)を設け、超過分はその日の
通知からは外れますが、監視自体は続きます。決算発表が近く一旦様子見と
なっている銘柄も、同様に決算発表までの営業日数を添えて毎営業日通知します。

**売買クールダウン**: 保有銘柄の一覧の変化(前回と比べて新規購入・買い増し・
一部売却・全部売却のいずれかが起きたと推定できる場合)を検知すると、
その銘柄については一定期間(新規購入・全部売却は既定5営業日、買い増し・
一部売却は既定3営業日)、通常の買い・売り推奨通知を抑止します(「買った
ばかりの銘柄にまた買い通知が来る」といった煩わしさを防ぐため)。この
抑止は、6節の売却・利確判定を含め、保有銘柄に関するすべての通常通知に
共通して適用されます。ただし、6.x節の重大リスク(緊急に保有内容を確認
すべき水準)の通知はこのクールダウンを貫通し、必ず届きます。全部売却の
あとも、抑止期間が終わるまでは内部記録を保持し続けるため、売った直後に
再びNEAR BUY等の通知が来ることはありません。

**通知本文の簡潔化**: NEAR BUY等の通知量が増えることに備え、LINE本文は
「判定・銘柄コード・銘柄名(必須)→現在値→目標価格や乖離率→連続監視日数→
理由→投資タイプ」の優先順位で、目安50文字・上限70文字程度に収めるように
しました(内部の記録・監査ログの情報量は一切減らしていません、あくまで
LINE本文の見せ方のみの変更です)。ただし重大リスクの通知は、必要な理由が
欠けることのないよう、この文字数上限を厳密には適用しません。同一銘柄・
同一実行内で複数の条件に同時に該当した場合も、優先順位(重大リスク>
買い水準到達>売却系>通常の買い候補>NEAR BUY>決算待ち)に従って1通に
まとめ、同じ銘柄について1回の処理で複数のLINEメッセージが送られることは
ありません。

### 5.9 通知簡潔化の実送信経路への接続・監視状態遷移通知・重複抑止(2026-08コードレビュー対応)

5.8節で述べた通知簡潔化の方針は、当初LINE本文生成の内部部品(整形ロジック)
としてのみ実装されており、実際にユーザーへ届くLINE通知本文はまだ旧来の
長文フォーマットのままになっていました。この改訂で、BUY・買い増し・NEAR
BUY・決算待ち・売却検討・重大リスクの各通知が、実際の送信経路で50/70文字
ルールに従うよう修正しました(before/afterレポート等、診断目的で完全な
理由・価格情報を必要とする画面は、意図的に従来の長文表示のまま維持して
います)。BUY候補まとめ通知(複数銘柄を1通にまとめるダイジェスト)の
1銘柄分のブロックも、同じ50/70文字ルールの短縮形式に統一しました。

**NEAR BUY監視からBUYへの到達・監視終了の実際の通知**: NEAR BUYで監視して
いた銘柄が実際に打診買い水準へ到達した場合、通常の「買い」ではなく
「到達」ラベルの通知とし、「◯日監視後」と何営業日監視していたかを表示
するようにしました。逆に、買い水準へ届かないまま監視条件から外れた
(値上がりして条件を外れた・企業として魅力度が低下した・データ取得不能が
続いた)場合は、連続監視日数が一定日数(既定5営業日)以上だった銘柄に
限り「監視終了」通知を送るようにしました(短期間だけ様子見した銘柄まで
逐一「終了しました」と知らせると煩わしいため)。実際に売買したことによる
監視終了(クールダウン起動時)は、この監視終了通知の対象にはしません
(ユーザー自身の行動の結果であり、あらためて知らせる必要が無いため)。
NEAR BUYで監視を継続していた銘柄について、データ取得エラーが続いて
連続監視日数の判定自体ができない期間を挟んだ後、その次に評価できた
営業日に実際に買い水準へ到達した場合は、「監視終了」通知は送らず
「到達」通知のみを送ります(2026-08-14追記)。

**買い候補Lambdaと保有銘柄Lambdaをまたいだ重複抑止**: 同じ銘柄について、
買い候補側と保有銘柄側の両方から同じ日に通知が発生しうる場合、後から
発生した通知の重要度が既に送った通知以下であれば送信を見送るようにしま
した(重要度の順序: 重大リスク＞買い水準への到達＞売却検討＞通常の買い
候補＞NEAR BUY＞決算待ち)。逆に、NEAR BUYの通知を送った後に同じ銘柄で
売却検討や重大リスクが判明した場合は、順序に関わらず必ず届きます(重要度
の高い通知が低い通知に隠れることはありません)。この仕組みは完全な排他
制御ではなく、同じ日にどちらのLambdaが先に評価を終えたかによる、ベスト
エフォートの重複抑止です。

## 6. 保有銘柄の見直し判定(利確・売却の考え方)

これがこのシステムの中核機能です。単純な「株価が上がったから売れ」という
判定ではなく、複数の視点を組み合わせて慎重に判定する設計になっています。

以下の6.1〜6.8節は、**「投資した前提が崩れていないか」を判定する部分
(6.3節の「売却を検討」「至急確認」「人的確認が必要」等のラベル)** の
現在(2026-08-06時点)の挙動です。この部分は将来、6.9節で説明する新しい
判定方式へ段階的に切り替わる予定ですが、本書執筆時点ではまだ切り替わって
おらず、以下の内容がそのまま使われています。なお、**利益確定(利確)に
関する判定(「一部売却を検討」「全部売却を検討(利確)」等)は、新方式に
切り替わった後も対象外で、常にこの節の方式のまま変わりません。**

### 6.1 判定は3つの視点を組み合わせて決まる

| 視点 | 何を見るか |
|---|---|
| ① 中身(ファンダメンタル)の判定 | 含み益の大きさ、適正価格からの乖離、配当利回りの低下、成長の鈍化など、「会社の価値に対して株価が割高になっていないか」を見る |
| ② タイミング(値動き)の判定 | 直近の値動きが上昇トレンドか下降トレンドかを見る |
| ③ 最終判定 | ①と②を組み合わせて決める。**上昇トレンドは①の判定を1段階までしか弱めない**(例: 「全部売却検討」→「一部売却検討」)。下降トレンドが①の判定を強めることもない(あくまで①の判定材料の一つとして使われるのみ) |

このように分けている理由は、「株価が上がっているから」という理由だけで
利確判定を弱めすぎたり、逆に「一時的に下がっているから」という理由だけで
判定を強めすぎたりしないようにするためです。

### 6.2 大事な設計方針: 含み益の大きさ「だけ」では強い判定は出さない

含み益率がどれだけ大きくても、それ単独では「一部売却検討」「全部売却検討」には
なりません。必ず、含み益に加えて、適正価格からの超過・配当利回りの低下・
成長鈍化・トレンド転換など、**複数の独立した根拠が同時にそろって初めて**
利確判定が強まる設計になっています。逆に、明確に強い根拠(投資前提が崩れた、
不祥事が確定した、自分で設定した目標株価に到達した、など)が1つあれば、
それだけで強い判定(全部売却検討)になることもあります。

### 6.3 判定ラベルの一覧と意味

保有銘柄について実際にLINEへ表示されるラベルです。

| 通知に表示されるラベル | どんな時に出るか |
|---|---|
| (通知なし・保有継続) | とくに気になる兆候がない、通常の状態 |
| 保有継続(監視) | 含み益がやや出ている、または株価が適正価格をやや上回っている程度。まだ利確を積極的に考える段階ではないが、一応注視しておく状態 |
| 保有継続(決算待ち) | 上と似た状態だが、決算発表が近いため、新しい決算内容が出るまで様子を見る状態。この状態のときは通知本文の「判定」欄が「暫定判定」に変わり、次回決算まで何営業日かという「判断保留理由」があわせて表示される(2026-07-31改訂) |
| 一部売却を検討 | 複数の根拠が重なり、保有株数の一部だけ売って利益を確定させることを検討してよい状態 |
| 一部縮小を検討 | 利確とは別に、決算発表が近いことを理由にリスクを一部減らすことを検討する状態(現状の通知ではあまり使われていません) |
| 全部売却を検討(利確) | 強い根拠が1つ、または複数の中程度の根拠が重なり、保有株を全部手放すことを検討してよい状態(投資前提が崩れたわけではなく、あくまで「利益を確定する」観点での判定) |
| 要確認(決算前) | 本来なら一部/全部売却検討に相当する状態だが、決算発表の直前のため、具体的な売却価格は示さず「決算後に改めて確認」を促す状態 |
| 要確認(決算後) | 直近で決算が発表されたばかりで、新しい数字を踏まえて改めて確認したほうがよい状態 |
| 要確認 | 投資前提に関わる懸念材料が1つだけ見つかったが、売却を勧めるほどの根拠の数はそろっていない状態 |
| 売却を検討 | 投資前提が崩れつつある(業績・配当・財務などの悪化)という独立した根拠が複数そろった状態。利確目的ではなく、「持ち続ける前提が崩れてきている」という観点の判定 |
| 至急確認 | 債務超過・上場廃止リスク・重大な不祥事など、緊急性の高い懸念が、公式発表で確定した状態。最も強い警告レベル |
| 人的確認が必要 | システムが「売却検討」「至急確認」を出そうとしたが、根拠の独立性など内部の安全チェックに引っかかったため、自動判定をいったん止め、利用者自身の確認を促す状態(6.5節) |
| 保有比率を確認 | 個別銘柄の良し悪しとは関係なく、その銘柄がポートフォリオ全体に占める割合が大きくなりすぎている状態(6.6節) |

「保有継続(監視)」「保有継続(決算待ち)」のLINE通知本文の見出しは、以前は常に
「割高水準を監視」固定でしたが、2026-07-31改訂で状況に応じて次の4通りに
出し分けるようにしました(判定ロジック自体は変更していません)。

| 見出し | 出る条件 |
|---|---|
| 適正価格超過・決算後に再評価 | 決算発表待ちのため最終判定を保留している状態(上表の「保有継続(決算待ち)」) |
| 保有継続・データ確認待ち | 適正価格そのものが算出できていない状態 |
| 適正価格のばらつき大・継続監視 | 適正価格算出の信頼度が低い、または算出手法間の差が大きい状態 |
| 割高水準を監視 | 上記のいずれにも該当しない、通常の監視状態 |

### 6.4 通知に出てくる複数の「価格」の意味

利確・売却の通知には、状況に応じて次のような価格が表示されます。すべてが
毎回表示されるわけではなく、算出できない場合は「算出不可」と表示されます。

| 価格の種類 | 意味 |
|---|---|
| 一部利確検討開始価格 | この価格を超えたあたりから、一部売却を考え始めてよい目安 |
| 指値の目安価格 | 実際に指値注文を出すならこのあたり、という参考価格 |
| 全部利確再検討価格 | この価格に到達したら、全部売却をあらためて検討してよい目安 |
| 即時執行目安価格 | 「至急確認」など、すぐに検討すべき状況のときだけ表示される、今まさに参考にできる価格 |
| 上昇時の再評価価格 | 株価がここまでさらに上昇したら、利回りなどを見直すきっかけにする価格 |
| 下落時の再評価価格 | 株価がここまで下落したら、投資の前提自体が崩れていないか見直すきっかけにする価格 |

以前のバージョンでは、これらの価格が「必ず現在株価以上になるように」機械的に
補正されており、判定内容と価格が矛盾して見える不具合がありました。現在は
その補正を廃止し、算出できない場合は素直に「算出不可」と表示するように
修正済みです(10節「制約事項」も参照)。

「打診」という表現は打診買い価格(買いの目安価格)専用の言い回しであり、
売却検討の簡潔通知(5.9節)では使いません。即時執行目安価格を表示する
場合は「即時執行」、下落時の再評価価格(投資前提再確認価格)を表示する
場合は「見直し」というラベルを、それぞれ表示する価格の意味に応じて
使い分けます(2026-08-14追記)。

#### LINE通知とシステム内部の判断根拠を分離(2026-08-14追加)

本番環境でのVALIDATIONモード実通知レビュー(2026-08-14実施、12銘柄)を受け、
LINE通知本文の設計方針を変更しました。LINE通知の目的は「利用者が次の行動を
数秒で判断できること」であるとし、以下の情報だけを通知本文に含め、それ以外の
判断根拠(適正価格の算出手法別内訳・信頼度・独立根拠数・一次情報確認状況・
データ品質チェックの詳細・監視条件の長文・反対材料の長文等)は、引き続き
Recommendation・監査ログ(12.3節)にのみ記録し、通知本文には出さないように
しました(判定ロジック自体・記録される情報量は変更していません)。

- 判定/アクション(絵文字付きの見出し)
- 銘柄コード・銘柄名
- 現在価格
- 買い/売りの目安価格(算出できない場合は「算定保留」と明示し、以前のように
  現在値等へ機械的に補正した数値を表示することはしない)
- 必要に応じた補助情報(1行程度の理由)

上の6.3節の判定ラベル一覧は、内部の「判定区分」の意味を示すものとして
引き続き有効ですが、実際にLINEへ表示される見出し・価格ラベルは次のとおり
簡潔化しています(6.4節の価格の意味も参照)。

| 内部の判定区分 | 実際にLINEへ表示される見出し | 目安価格のラベル |
|---|---|---|
| 買い(通常) | 🟢買い | 打診/通常(2種類併記) |
| NEAR BUY監視 | 🔵監視(打診買い接近) | (価格ラベルなし) |
| NEAR BUY→買い水準到達 | 🟢到達 | 打診/通常 |
| 決算発表接近の様子見(買い側) | 🔵監視(決算待ち) | (価格ラベルなし) |
| 保有継続(監視)・保有継続(決算待ち)・ポートフォリオ集中リスク | 🟡監視 | 利確検討(利確監視のみ表示。無ければ「価格目安は算定保留」) |
| 一部売却を検討・一部縮小を検討 | 🟠一部売却/🟠一部縮小 | 売却目安(無ければ「売却目安は算定保留」) |
| 全部売却を検討(利確)・売却を検討(全部売却相当) | 🔴全部売却検討 | 全部売却目安(無ければ「全部売却目安は算定保留」) |
| 売却を検討(通常) | 🔴売却検討 | 見直し(無ければ「売却目安は算定保留」) |
| 要確認(決算前)・要確認(決算後)・要確認・人的確認が必要 | ⚠️要確認 | 「売買判断を保留」の一言のみ(価格は表示しない) |
| 至急確認 | 🔴緊急確認 | 即時執行(あれば) |
| 監視終了 | (5.9節のとおり) | - |

適正価格(Fair Value)が判定に使えないと内部で明示的にマークされている場合、
以前は目安価格の構成時だけ無条件にこの適正価格を使ってしまい、「判定には
使わないと決めた適正価格を、目安価格には使ってしまう」という矛盾がありました
(2026-08-14実通知レビューで発覚した不具合)。修正後は、目安価格候補の算出
時にも判定と同じ使用可否基準を適用し、判定に使えない適正価格に由来する候補は
自動的に除外します。取得単価ベースの候補(含み益目標等)は影響を受けず引き
続き算出されるため、「適正価格が使えない=目安価格が全て算定不能」という
意味ではありません(候補が1つも残らなかった場合のみ「算定保留」と表示
します)。

### 6.5 「人的確認が必要」という安全装置について

「売却を検討」「至急確認」といった強い判定を自動で出す前に、システムは
内部で次のようなチェックを行います。

- 根拠が十分に独立した複数の材料に基づいているか(同じ問題を言い換えただけの
  根拠を、別々の根拠として二重に数えていないか)
- 判定の信頼度が、実際にそろっている根拠の数に見合っているか
- 一次情報(会社の公式発表)で確認できていない情報だけを根拠にしていないか

これらのチェックに引っかかった場合、自動での「売却検討」通知は送らず、
代わりに「人的確認が必要」という通知に切り替わります。この場合、
自動的な売却推奨はいったん保留され、利用者自身の目でもう一度確認することが
求められます。**間違った売却提案を自信満々に出してしまうより、判断に迷いが
ある場合は率直に「わからないので確認してください」と伝える**、という設計方針です。

### 6.6 ポートフォリオの集中リスクについて

個別銘柄の業績や株価が良好でも、**その銘柄1つに資産が偏りすぎている**こと
自体がリスクになります。このシステムは、保有銘柄それぞれについて、
「時価総額ベースでポートフォリオ全体の何%を占めているか」「取得価格ベースで
何%を占めているか」を計算し、どちらかが基準値(初期設定では20%)以上になった
場合、その銘柄単体の判定とは別に「保有比率を確認」という通知を送ります。
この判定はモデルによる推測ではなく、保有データからの単純な計算(事実)なので、
常に信頼度「高」で通知されます。

なお、業種(セクター)単位での集中リスク(例:銀行株ばかり持っている、など)の
自動チェックは、現時点では実装されていません。個別銘柄1つあたりの比率のみが
対象です。

### 6.7 決算発表の前後だけの特別ルール

決算発表の直前(目安として数営業日前)は、直近の数字がまだ古い可能性があるため、
利確判定が「一部/全部売却検討」になりそうな場合でも、**具体的な売却価格は
示さず**、「決算後に改めて確認してください」という通知(要確認(決算前))に
切り替わります。

一方、「投資前提が崩れた」ことによる売却判定(6.3節の「売却を検討」
「至急確認」)は、決算前後であっても抑制されません。すでに確定している
悪材料を、決算発表を待つという理由で見逃すべきではない、という考え方です。

#### 決算発表予定日を過ぎたのに発表実績を確認できない場合(2026-08-06追加)

無償のデータ源(yfinance等)は更新が遅れることがあり、「次回決算発表予定日」
として、実際にはもう過ぎてしまった過去の日付が返ってくることがあります。
このような過去日をそのまま「次回決算」として通知に表示してしまうと、
「〇月〇日に決算発表予定」という、すでに終わっている予定を今後の予定であるかの
ように案内してしまう不具合になります(2026年8月に実際に発生した事例)。

このため、取得した予定日がすでに過去の日付だった場合は「次回決算日」としては
**使用しません**(通知にも表示しません)。そのうえで、以下のように扱います。

- 決算予定日を過ぎたが、財務データ(決算期末日)がまだ更新されていない
  ように見える間は、通常の「一部/全部利確検討」の提案を保留し、
  「決算発表状況確認待ち」という通知に切り替えます。この通知では
  「決算は発表された」とも「まだ発表されていない」とも断定しません
  (無償データだけでは確認できないため)。
- その後、財務データの更新(決算期末日の前進)が確認できれば、通常の
  利確判定に戻ります。
- 財務データの更新確認が長時間(既定48時間)経っても取れない場合は、
  「確認が長引いています」という文言に切り替わります(通知は状態が
  変わった時点で再送されます。同じ状態が続く間は毎回送り直しません)。

なお、この扱いは銘柄コードを問わず同じロジックで行われます(特定の銘柄だけ
特別扱いする、といったことはありません)。

#### デプロイ前の追加対応(2026-08-06追加)

上記の仕組みについて、実運用に入る前に以下の3点を強化しました。

- **日本時間(JST)基準への統一**: 決算予定日が「今日から見て過去か未来か」の
  判定・決算までの営業日数計算は、必ず日本時間の暦日を基準に行うよう統一しました
  (システム内部の時刻はUTC(協定世界時)で扱っているため、単純にUTCの日付で
  判定すると、日本時間の深夜0時〜午前9時の間は実際には日本時間で当日・翌日に
  入っているのに前日と誤判定してしまう可能性がありました)。
- **財務データが「更新済み」と判定する条件を厳格化**: これまでは決算期末日
  (fiscal_period_end)だけを見ていましたが、その財務データを実際に取得した
  タイミングが決算予定日より前(=決算発表前から保持していた古いデータの
  可能性がある)である場合は、「更新済み」とは判定しないようにしました。
- **古すぎる過去日で判定が止まったままにならないようにする安全策**: データ
  提供元が何か月も前の古い決算予定日を返し続けた場合に、「決算発表状況確認待ち」
  の状態から抜け出せなくなる(=一部/全部利確の提案が永久に保留され続ける)
  ことを防ぐため、過去の決算予定日から一定日数(既定10日)を超えて経過しても
  なお財務データの更新が確認できない場合は、現在の判断への関連性が薄いと
  みなし、通常の利確判定へ復帰するようにしました。

なお、決算日の状態を表す内部区分「CONFIRMED」は「取得できた決算予定日が
評価日時点で過去日ではない(当日または未来日)」という意味であり、「決算発表が
確認された」という意味ではありません(無償データからは決算発表の実施自体を
確認できないため、発表済みかどうかは常にUNCONFIRMED相当の扱いです)。

#### 財務データ更新確認の精度向上(2026-08-07追加)

決算期末日(fiscal_period_end)は、データ提供元(yfinance)からは**年次決算の
期末日**として取得されます(直近四半期の期末日ではありません)。3月決算の企業が
8月に第1四半期決算を発表しても、この値は3月末のままとなるため、これだけを
見て「決算発表が財務データへ反映されたか」を判定すると、四半期決算の反映を
検知できないことが分かりました。

このため、決算発表が反映されたかどうかの確認には、取得できる範囲の四半期
実績データ(直近の複数四半期分)のうち最新の期末日を優先して使うように
変更しました。四半期実績データが取得できない銘柄でのみ、従来通り年次決算
期末日を代替として使います(この場合、年次決算より後に発表された四半期決算の
反映は検知できないという制約が残ります)。どちらの情報も取得できない場合は
「確認不能」として扱い、これまで通り無理に財務データ取得日時で代替すること
はありません。

あわせて、以下の安全策を追加しました。

- 財務データの取得タイミングが決算予定日より前の場合、その財務データの
  期末日がどれだけ新しく見えても「更新済み」とは判定しません(決算発表前から
  保持していた古いデータの可能性があるため)。
- データ提供元の異常等により、評価日より未来の期末日が返ってきた場合、
  それを「決算発表が反映された証拠」として使いません。
- 決算反映確認に実際に使った期末日とその由来(四半期実績由来か、年次決算の
  代替か、確認不能だったか)を監査ログへ記録するようにしました。

#### 由来の記録をさらに正確にする(2026-08-07追加)

上記の「四半期実績データ」は、データ提供元(yfinance)から四半期単位のデータを
取得できない銘柄では、社内的に年次決算データへ振り替えて代用しています。この
振り替え自体は既存の仕組みですが、当初は監査ログ上で「四半期実績データを使った」
のか「実際には年次決算データへの振り替えだった」のかを区別できていませんでした。

このため、監査ログには実際にどちらを使ったかを明示するようにしました。四半期の
実データそのものを使えた場合と、年次決算データへ振り替えた場合を分けて記録する
ことで、「決算発表が反映されたと判定した根拠が、本当に四半期の実績なのか、
それとも年次データの代用に過ぎないのか」を後から確認できます。年次データへの
振り替えが発生している銘柄では、期中に発表された決算の反映を検知できない場合が
あるという制約は変わりません(無償データを利用している以上の既知の制約です)。
確認できなかった場合に、取得日時や推測で埋め合わせることはしません。

### 6.8 判定の「信頼度」について

すべての判定には信頼度(高/中/低)が付きます。これは「この提案がどれくらい
魅力的か」ではなく、**「この判定の元になったデータや分析が、どれくらい
信頼できるか」**を表しています。たとえば次のような場合は、たとえ判定内容が
強いものであっても信頼度が「高」にはなりません。

- 決算発表が近く、直近の数字がまだ反映されていない
- 適正価格の計算方法が複数あるうち、方法同士の結果が大きくばらついている
- 必要なデータの一部が取得できていない
- 一次情報(会社の公式発表)による裏付けがなく、外部データのみに基づいている
- 銀行・リース業など、通常の計算方法が当てはまりにくい業種で、専用の評価方法が
  用意されていない銘柄である
- 根拠が「適正価格の計算結果」1つだけで、他の裏付けがない

「保有継続(監視)」のLINE通知には、意味の異なる2つの信頼度が別々のラベルで
表示されます(2026-07-31改訂。以前はラベル無しの「信頼度:」がもう1つ重複して
表示されており、どちらの信頼度を指しているか分かりにくい状態でした)。

| ラベル | 意味 |
|---|---|
| 適正価格算出の信頼度 | 適正価格そのものの計算結果がどれだけ確からしいか |
| 保有継続判定の信頼度 | 「まだ売却を検討する段階ではない」という判定自体がどれだけ確からしいか |

### 6.9 保有判断の新方式(保有判断スコア)への段階移行について(2026-08-06追加)

これまでの6.1〜6.8節の判定(個別の悪化シグナルを積み上げて「売却を検討」
「至急確認」等を判定する方式、以下「従来方式」)に加えて、それらを1つの点数に
統合した新しい判定方式(以下「保有判断スコア方式」)を用意しました。
**ただし、本書執筆時点(2026-08-06)では、実際に届く通知はすべて従来方式に
よるものです。新方式は今のところ舞台裏で計算・記録されるだけで、通知には
まだ使われていません。** 段階的に切り替えるための仕組みとして、あらかじめ
用意してある状態です。

対象となるのは、6.1〜6.8節と同じく「投資した前提が崩れていないか」の判定
部分だけです。利益確定(利確)に関する判定は、この新方式に切り替わった後も
影響を受けず、常に従来どおりのロジック(6.4節の各種価格の算出方法を含む)の
ままです。

#### 新方式の考え方

新方式は、次の3つの点数を1つに合算し、**合算した点数がマイナス1点を
下回った場合にのみ**LINEで通知します。「①→②→③と条件を順に絞り込む」
という従来方式の考え方とは異なり、最初からすべての観点を1つの点数として
合算する方式です。

| 点数 | 何を見るか | 満点 |
|---|---|---|
| 企業品質スコア | 評価時点の会社の体力(財務健全性・キャッシュ創出力・収益力・業績安定性・ガバナンス) | 50点 |
| 投資ストーリー維持スコア | 保有を続けている理由(配当方針・利回り・優待・利益や財務の前提・銘柄固有の購入理由)が今も崩れていないか | 50点 |
| リスク控除スコア | 直近で新たに発生した悪化事象の重さ | 最大100点の減点 |

保有判断スコア = 企業品質スコア + 投資ストーリー維持スコア − リスク控除スコア

新方式での判定ラベルと、対応する保有判断スコアの目安は次のとおりです
(0点以上の範囲は、内部的にはさらに保有の強さに応じて4段階に分かれますが、
いずれも通知はしません)。

| 判定ラベル | スコアの目安 | 通知 |
|---|---|---|
| (通知なし・保有継続) | 0点以上 | しない |
| (通知なし・要注意) | マイナス1点以上0点未満 | しない |
| 売却を検討 | マイナス30点超マイナス1点未満 | する |
| 全部売却を強く検討 | マイナス30点以下 | する |
| 重大条件のため緊急確認 | 債務超過・重大な粉飾決算・上場廃止決定など、一次情報で確認できた重大な事実がある場合(該当時はスコアも自動的にマイナス30点以下まで押し下げられます) | する |

従来方式と同じく、データが十分に揃っていない項目を推測で埋め合わせることは
しません。企業品質・投資ストーリー・リスク控除それぞれについて、実際に
評価できた項目の割合(カバー率)を記録しており、カバー率が低すぎる銘柄は、
一次情報で確認できた重大な事実がある場合を除き、通知そのものを見送ります。
新方式に切り替わった後、投資ストーリーの「今も崩れていないか」の基準
(いつ時点の状態と比較するか)は、原則として利用者自身が確認・承認した
内容を優先して使い、確認前は控えめな採点(過大評価をしない)にとどめます。

#### 現時点の運用状況(2026-08-06時点)

新方式は3段階で切り替える設計になっています。

1. **現在地: 見送り段階(従来方式のみ稼働)** — 新方式は舞台裏で計算・記録
   だけ行われ、通知には一切使われません。実際に届く通知はすべて6.1〜6.8節の
   従来方式によるものです。
2. **試験段階(比較検証)** — 新方式も同時に計算しますが、通知は引き続き
   従来方式のみが行います。新旧の判定結果を比較したうえで、次の段階へ
   進めるかどうかを判断します。
3. **本稼働段階** — 新方式が実際の通知を担当するようになり、従来方式は
   通知を出さなくなります(内部的な判定自体はその後も記録され続けます)。

どの段階を使うかは、利用者が明示的な操作で切り替えるまで変わりません
(自動では切り替わりません)。銀行・保険・証券などの金融業の銘柄については、
新方式に必要な専用の評価データ・評価方法がまだ用意できていないため、
本稼働段階に切り替わった後も、当面は引き続き従来方式が通知を担当します。

切り替え操作の具体的なコマンドは[運用手順書](operations_manual.md)を
参照してください。

#### 緊急停止(kill switch)について(2026-08版で適用範囲を拡大)

誤判定の疑い等で「今すぐすべての保有銘柄関連の通知を止めたい」場合に使う
緊急スイッチです。段階(見送り/試験/本稼働)の切り替えとは別に、いつでも
オン・オフできます。

- **止まるもの**: 売却検討の通知(新旧どちらの方式でも)・利益確定検討の
  通知・保有比率が偏りすぎている場合の通知・1日の処理が終わったあとの
  まとめ通知(10.2節)。
- **止まらないもの**: 内部の判定処理そのもの・判定結果の記録。緊急停止中も
  裏側では通常どおり判定・記録が続くため、停止解除後にさかのぼって
  状況を確認できます。

## 7. 適正価格の考え方

このシステムは「この株の本当の価値はいくらか」を1つの数字で断定しません。
複数の計算方法で見積もり、**弱気(bear)・中立(neutral)・強気(bull)の
3つの幅**として表示します。これは、1つの計算方法だけに頼ると計算方法特有の
クセに引きずられてしまうためです。

### 7.1 使っている計算方法

| 方法 | 考え方 |
|---|---|
| 配当利回り基準 | 「この配当額なら、株価がいくらなら魅力的な利回りといえるか」から逆算する |
| 総合利回り基準 | 配当に株主優待の価値も加えて、同様に逆算する |
| PER基準 | その銘柄自身の過去の株価収益率(PER)の平均的な水準と、今期の予想利益から見積もる |
| PBR基準 | 同様に、その銘柄自身の過去の株価純資産倍率(PBR)の平均的な水準から見積もる |
| 過去の値動き基準 | 過去の安値圏(52週安値・より長期の安値)を参考に、下値の目安を見積もる |
| 簡易DCF | 会社が生み出す将来のお金(キャッシュフロー)を見積もり、現在の価値に割り引いて計算する簡易的な方法 |

**注意**: PER・PBRは、同業他社や市場全体との比較ではなく、**その銘柄自身の
過去の水準**とだけ比較しています(業界平均データを取得する仕組みが
まだ無いためです)。また簡易DCFは、本来必要な金利・株式リスクプレミアムなどの
データが揃わないため、簡略化した固定の割引率を使っています。この2点の理由から、
簡易DCFの結果は信頼度が「中」より上にはならないようにしてあります。

計算できない方法は無理に埋めず、単純に除外されます。計算できた方法が
少なすぎる場合や、方法同士の見積もりが大きく食い違っている場合は、
「この適正価格は判断材料として使うには不十分」という扱いになり、
その旨が通知にも表示されます。

## 8. 株式分割・企業行動への対応

株式分割(例: 1株を5株に分割)が起きると、株数は増え、1株あたりの価格は
下がりますが、**会社の価値そのものは変わりません。** この調整をせずに
以前のデータと単純比較すると、「株価が8割下落した」「配当が急に減った」
ように見えてしまう、という誤検知が過去に実際に発生していました
(10節参照)。

- **自動で検知できるもの**: 通常の株式分割・株式併合のみ、データ提供元
  (yfinance)から自動で取得できます。
- **手動登録が必要なもの**: 無償割当、会社分割(スピンオフ)、証券コード変更、
  合併、上場廃止、配当基準日の変更などは、自動取得できるデータ源が
  無いため、株主優待と同様に、確認した利用者が手動で登録する必要があります。
- 分割が検知されると、保有銘柄の「株数」「平均取得単価」を過去にさかのぼって
  再計算する機能(`recompute-all`)があります。もともとの購入記録
  (いつ・何株・いくらで買ったか)自体は書き換えず、そこから導き出される
  現在の株数・平均取得単価だけを再計算します。

### 8.1 減配(配当が減った)の判定

配当が前より少なく見える場合、それが「本当に会社が配当を減らしたのか」
「単に株式分割で1株あたりの金額が薄まっただけなのか」を区別します。

| 判定結果 | 意味 |
|---|---|
| 減配(実績確定) | すでに確定した過去の配当実績同士を比較して、実際に減っている |
| 予想減配(未確定) | 会社が発表した「今後の見通し」ベースの比較で減っている(まだ確定ではない) |
| 分割調整のみ(実質的な減配ではない) | 見かけ上は減っているが、株式分割の影響を調整すると実質的には減っていない |
| 配当維持 / 増配 / 比較不可 | 文字どおりの意味 |

「予想」と「確定」を区別しているのは、確定した減配は動かしようのない事実
ですが、予想はまだ変わる可能性があるためです。同じ強さの警告として
扱ってしまうと、確度の違いが利用者に伝わらなくなってしまいます。

### 8.2 配当データの複数ソース照合(クロスバリデーション)

配当データは主データ源(yfinance)と副データ源(EDINET、金融庁のシステム)を
突き合わせ、両者の金額が大きく食い違う場合は「データの信頼性が確認できない」
として、その銘柄を買い候補の判定対象から除外します(誤ったデータに基づいて
購入を勧めないための安全側の設計)。

2026-08改訂前は、この突き合わせを「主データ源の最新値」と「副データ源の
最新値」を単純に比較する方式で行っていました。しかし主データ源は暦年
(1月〜12月)で配当を集計するのに対し、副データ源は各社の決算期
(例: 4月〜翌3月)で集計するため、決算期が1月〜12月からずれている会社では
比較している期間そのものが一致しておらず、実際には配当額が一致していても
「食い違い」と誤判定され、買い候補から除外され続けてしまう不具合があり
ました(発覚のきっかけとなった銘柄: 4193・5195・8136)。

**修正内容**: 両データ源とも、各社の決算期(会社ごとの決算月)を基準に
複数期分の配当実績を保持するように変更し、その中から両方のデータ源で
実際に照合できる決算期(通常は直近の共通決算期)を探して、その期同士で
比較する方式に改めました。副データ源(EDINET)側の提出には日単位の
タイムラグが日常的に発生するため、主データ源側の最新決算期がまだ
副データ源に反映されていない場合は、1つ前の共通決算期で照合します。
なお、買い候補判定などで実際に使う配当額は、照合の成否に関わらず常に
主データ源(yfinance)の最新値です。「どの期まで照合できたか」は判定用の
配当額そのものには影響を与えず、別の記録として保持します。

決算期の途中で株式分割等が発生した場合、副データ源(EDINET)の年間合計値には
中間配当・期末配当の内訳や発生日の情報が無いため、単一の分割比率では
正しく換算できません。このようなケースでは無理に換算して比較することはせず、
「まだ照合できない」(除外はしない)という扱いにします。決算期の終了後にのみ
株式分割が発生した場合は、年間合計値全体を正式な累積換算係数で換算してから
比較します(8136はこのパターンに該当)。

会社の決算月が取得できていない銘柄は、暦年集計での代用値のみが得られる
ため、副データ源の決算期とたまたま一致しても「照合できた」とは扱わず、
常に「まだ照合できない」として扱います(異なる集計基準の値を偶然の一致
だけで正しいと断定しないため)。

これらの見直しにより、照合できる期間さえ見つかれば「まだ照合できない」
扱いとなり、真に金額そのものが食い違っている場合(同じ決算期同士を
正しく比較しても一致しない場合)のみ、従来どおり買い候補から除外されます。

## 9. 自動実行のスケジュール

AWSへデプロイした後は、次の時刻(すべて日本時間)に自動で実行されます。
利用者側で何かを起動する必要はありません。

| 時刻(平日) | 内容 |
|---|---|
| 08:00 | 保有銘柄・ウォッチリストの中から買い候補(新規購入・買い増し)を探して通知(2026-07-31改訂。5.6節)、および保有銘柄の利確・売却チェック・ポートフォリオ集中チェック(2026-07-31改訂: 従来16:30実行だったものを、買い候補分析と処理条件・通知タイミングを揃えるため08:00へ変更) |
| 10:00 / 12:30 / 15:30 | 保有銘柄の新規の公式発表(適時開示)にリスクがないかチェック |
| 18:00 | 過去の判定が実際どうなったかの振り返り(結果はLINE通知なし。記録のみ。2026-08改訂で、推奨後7日時点の確認を追加。12.1節) |

| 頻度 | 内容 |
|---|---|
| 毎週土曜07:00 | 候補銘柄一覧から条件を満たす銘柄をウォッチリストへ自動追加(5.7節。追加が1件以上あった場合のみLINE通知) |
| 毎週月曜19:00 | 前週に確定した振り返り結果を分析し、判定ロジックの改善が必要と判断した場合のみ改善タスクを登録してLINE通知(2026-08改訂。12.4節。以前の「毎週土曜09:00に全期間合算の成績レポートを送信」は廃止) |
| 毎月第1土曜10:00 | (2026-08改訂)月次の成績レポート自動送信は廃止。内部記録のみ行い、LINE通知はしない |
| 1・4・7・10月の第1土曜11:00 | (2026-08改訂)四半期の固定リマインド送信は廃止。内部記録のみ行い、LINE通知はしない(ルール変更提案自体は今まで通り自動生成されません。11節参照) |

一括で処理すると時間がかかりすぎるため、内部的には銘柄1件ずつ個別に
並行処理する仕組みになっています。利用者から見た結果(通知される内容)には
影響しません。

## 10. LINEでの通知・操作方法(概要)

### 10.1 通知の共通ルール

- 前回と実質的に同じ内容の通知は、重複して送られません。同じ種類の通知が
  再送されるのは、「前回と判定の種類が変わった」「価格が前回から3%以上動いた」
  「前回の通知から5日以上経過した」のいずれかに該当した場合のみです。
- どの通知にも、通知を一意に識別する「通知ID」と、「最終的な投資判断は
  利用者が行ってください」という注意書きが必ず添えられます。
- データ品質に矛盾が見つかった場合(内部の整合性チェックに引っかかった場合)は、
  個別にLINEへ通知せず、1日の処理が終わった後の「まとめ通知」の件数の中に
  含まれます(不具合を隠すのではなく、件数としては必ず可視化されます)。

### 10.2 1日の処理が終わったあとの「まとめ通知」

買い候補分析の「まとめ通知」は、「処理結果:」という見出しのもとに
「個別通知送信/通知不要(保有継続)/要確認/データ不足/再通知抑止/
処理失敗」の内訳件数を箇条書きでまとめた通知が1件送られ、続けて対象件数が
表示されます(2026-07-31改訂。以前は「判定の結果(保有継続など)」と
「通知処理の結果(送信した/抑止したなど)」が同じ並びで表示され、意味が
伝わりにくいという指摘を受け、見出しを付けて整理しました。内訳の集計方法
自体は変更していません)。内訳の合計が対象件数と一致しない場合は、
その旨も通知本文に明記されます(数字のズレを隠しません)。

保有銘柄・ウォッチリストの「まとめ通知」は、2026-08-14改訂(6.4節の
LINE通知/判断根拠分離)にあわせて、行動中心の4分類(売却・監視・要確認・
緊急確認)の件数のみを1行で表示する形式に変更しました。「売却」には
一部売却・全部売却検討の両方を合算します(内訳をこの通知上で分離することは
しません)。「緊急確認」(至急確認)は投資前提の悪化を意味するとは限らない
ため「売却」件数には含めず、独立した件数として表示します。緊急確認が0件の
日は、その項目自体を省略します。買い候補側のまとめ通知の内訳集計方法・
表示形式は変更していません。

なお、買い候補分析(08:00)と保有銘柄・ウォッチリストの利確/売却判定(08:00)は
別々のLambda関数として完全に独立して動作しており、それぞれ別々の「まとめ通知」
が送られます。保有銘柄の「まとめ通知」に買い候補の結果が含まれないのは
不具合ではなく意図した設計です。買い候補が1件も無かった日は、既定では
「まとめ通知」自体を送りません(`config/notification_rules.yaml`の
`send_empty_summary`で変更可能。保有銘柄側は対象外)。

### 10.3 LINEチャットからの操作

LINEのトーク画面から、次の3つの決まった書式のメッセージを送ることで、
CLIを開かなくても記録できます(自由な文章の解釈はせず、決まった書式のみに
対応しています。誤登録を防ぐためです)。

```
買付,銘柄コード,株数,単価      例: 買付,2914,100,3400
売却,銘柄コード,株数,単価      例: 売却,2914,50,4600
ウォッチ,銘柄コード           例: ウォッチ,7203
```

- 「買付」「売却」は、売買の記録を残すと同時に、保有銘柄のデータ(株数・
  平均取得単価)も自動で更新します。
- 「売却」は、保有株数を超える売却はできません。また、複数回に分けて買った株を
  売る場合は、購入日が古いものから順に売ったものとして計算します(先入先出)。
- あらかじめ登録した本人のLINEアカウント以外からのメッセージには反応しません。
- 手数料・税額・メモ・どの通知への対応かといった細かい情報は、この方法では
  登録できません。詳しく記録したい場合はCLI(運用手順書6節)を使ってください。

## 11. 判定ルールの変更について(なぜ勝手に変わらないか)

このシステムの判定基準(しきい値など)は、`config` フォルダの設定ファイルで
管理されていますが、**設定ファイルを直接書き換えない限り、判定ルールが
自動的に変わることはありません。** ルールを変更したい場合は、次の手順を
経る必要があります。

1. 変更したい基準について、過去の実績データをもとに「もしこの基準に変えて
   いたら結果はどうだったか」を試算する(対応できる項目は限定的です)
2. 変更理由・想定されるリスク・「たまたま過去データに当てはまっただけ」に
   なっていないかの評価・元に戻す条件、を文章として整理した変更案を作る
3. その変更案を、利用者自身が承認する
4. 承認された変更を、新しい「ルールのバージョン」として登録し、これも
   利用者自身が有効化して初めて、実際の判定に使われるようになる

どの段階も自動では進みません。**必ず人間の明示的な承認操作が必要**という
設計です。また、新しいルールに問題があった場合は、いつでも直前のバージョンに
戻すことができます。

四半期ごとのリマインド通知(9節)は、あくまで「見直しの時期が来ましたよ」と
知らせるだけで、変更案そのものを自動で作ることはありません。リスク評価などの
文章は人間の判断が必要な部分だからです。

## 12. 過去の判定を検証する仕組み

### 12.1 振り返り(点検)機能

システムが何か通知を出すと、その時点の株価が記録されます。一定の営業日数
(推奨の種類によって異なります)が経過した時点で、実際に株価がどう動いたか、
指定していた価格に実際に到達していたか、指標(TOPIX)と比べてどうだったかを
自動的に見直し、「その提案は結果的にどうだったか」を判定・記録します。
なお、配当や優待込みの正確なリターンまでは追跡していません(推測での
穴埋めをしないという方針のため、あえて算出していません)。

**2026-08改訂**: 上記の営業日ベースの振り返りとは別に、推奨から**暦日で
ちょうど7日後**(土日を挟んでも「7日」)の時点でも同様の振り返りを行うように
なりました。これは12.4節の週次改善判定が使う専用のデータであり、既存の
営業日ベースの振り返り(60日後・120日後など)の判定内容・通知には影響しません。

**WATCH等「監視継続」系の判定について**: BUY(購入)・SELL(売却)のように
「株価が上がった/下がった」だけで結果の良し悪しを機械的に判定できる推奨と
異なり、WATCH(監視継続)・決算発表待ち等の推奨は、そもそも「今すぐ売買する」
ことを意図した提案ではないため、株価の騰落だけでは自動的な成功/失敗を判定
できません。これらは「自動評価の対象外」として記録され、後述の成績集計
(12.2節)からも除外されます(**2026-08改訂**: 以前はこの「対象外」の推奨が
誤って成功率の計算に含まれ、常に「成功率0%」と表示されてしまう不具合が
ありました。対象外の推奨は成功率の分母からも正しく除外されるよう修正済みです)。

### 12.2 成績のまとめ

上記の振り返り結果を積み上げて、成功率や平均リターンなどを、判定の種類別・
信頼度別・ルールバージョン別に集計できます。これにより、「ルールを変えたら
実際に成績が改善したか」を後から確認できます。`jstock review report`
コマンド(手動実行)で、これまでの全期間を合算した成績を確認できます。
**2026-08改訂**: この全期間合算の集計は手動確認用の参考情報という位置づけに
変更しました。過去の古い判定ロジックによる成績と現在のロジックによる成績が
混ざってしまうため、次節の自動判定では使わず、直近週の実績のみを根拠にする
ように変更しています。

### 12.3 なぜその判定が出たのか調べる(監査ログ)

すべての判定について、入力に使った値・計算式・出力結果・データの取得元と
取得時刻が裏側で記録されています。`jstock audit show <銘柄コード>` という
コマンドで、過去のある判定について「何を根拠にその判定を出したのか」を、
ブラックボックスにせず後から確認できます。

### 12.4 週次の自動改善判定とGitHub Issue起票(2026-08追加)

**背景**: 以前は毎週土曜・毎月第1土曜に、それまでの全期間を合算した成績
サマリ(評価件数・成功率・平均リターンなど)をそのままLINE通知していました。
しかしこの通知だけでは「次に何をすればよいか」が分からず、また全期間合算では
過去の古いルールによる結果まで混ざってしまうため、現在のロジックを改善すべきか
どうかの判断材料としては不十分でした。

**新しい仕組み**: 毎週月曜19:00(その日18:00の振り返り完了後)に、
**前週(月曜〜日曜)に結果が確定した**7日後振り返り(12.1節)を、
「推奨の種類」×「その時点で使われていたルールのバージョン」の組み合わせ
ごとに集計します。過去の古いルールによる結果は現在のルールの成績とは
分けて集計されるため、「ルールを変えたら実際に良くなったか」を正しく
比較できます。

以下のいずれかに該当すると判断した場合、**改善が必要な候補**として記録します。

- 成功率、または指標(TOPIX)と比べた超過リターンが、種類ごとに定めた
  基準を下回った(評価件数が一定数に満たない場合は候補にしません)
- WATCH等「監視継続」系の推奨で、「自動評価の対象外」ばかりが続いている
  (=そもそも評価の仕組み自体を見直す必要がある可能性がある)

改善候補になっただけでは何もしません。**前週も同じ問題が続いている、または
悪化の程度が大きい**など、単発の悪い週だけではない十分な証拠がそろった場合に
限り、開発管理サービス「GitHub」上に**改善タスク(Issue)**を自動で登録し、
「ルール改善タスクを登録しました」というLINE通知を送ります。この通知には
対象の判定種別・件数・成績・登録したタスクへのリンクが含まれ、利用者は
その内容を確認し、必要であれば対応を検討する、という流れになります。

**改善候補が無い週・証拠が不十分な週は、LINE通知は一切送られません**
(「今週は問題ありませんでした」という通知も含め、何も送りません)。また、
AIが判定ロジックのコード自体を自動で書き換えることは今回は行いません。
あくまで「改善が必要そうな箇所を見つけて、人間に確認を依頼する」ところまでの
仕組みです。

**GitHub連携について**: この機能を実際に動かすには、事前にGitHub側の設定
(運用手順書参照)が必要です。設定が完了するまでの間は、改善候補の検出・
内部記録は通常通り行われますが、GitHub Issueの自動登録・関連するLINE通知は
行われません(エラーとして扱われることもありません)。

月次・四半期の従来の定型LINE通知(全期間合算レポート・固定リマインド)は、
「利用者が何か対応すべき場合のみ通知する」という上記の方針と矛盾するため
廃止しました。全期間の成績を確認したい場合は、引き続き`jstock review report`
コマンドを手動で実行してください。

### 12.5 判定精度向上機能・自己評価基盤(Phase A、2026-08追加)

**目的**: 「割安」「業績が良い」といった静的な評価だけでなく、株価タイミング・
決算サプライズ・過去の株価水準との比較・市場環境なども含めて総合的に判断する
仕組みを、段階的に追加していく計画の第一段階です。今回追加したのは、
将来のスコアリング機能そのものではなく、**「その判断が実際にどれだけ有効
だったかを後から検証できるようにする土台」**です。

**記録する内容**: 買い候補・売却・保有判断・利益確定の各判定が確定するたびに、
「その時点で実際に確定した最終判断値」(現在値・適正価格レンジ・信頼度など)を
不変の記録(DecisionSnapshot)として保存します。**現在のロジックを使って
過去の判断を後から再計算することは絶対に行いません**(記録した値だけが
正であり、ロジックを変更しても過去の記録は書き換わりません)。

**既存の振り返り機能をそのまま再利用**: この判断の成績を測るための株価
振り返り(5・20・60・120・250営業日後)は、新しい仕組みを別途動かすのでは
なく、既存の振り返り機能(12.1節)が既に算出している結果をそのまま使います。
同じ推奨について二重に振り返り処理を行うことはありません。

**現時点でできること・できないこと**: 今回の段階では、企業評価・タイミング
判定などのスコア自体はまだ何も計算されておらず、すべて「未評価」のまま
記録されます。`jstock decision-performance summary`コマンド(手動実行)で、
記録された判断の件数・成功率・平均リターン・中央値リターン等を確認できますが、
スコアによる絞り込みや、今どのタイミングで買うべきかといった具体的な助言は
まだ出せません。セクター(業種)別の株価指数との比較も、比較に使う適切な
指数が確定していないため、この段階では未対応です(将来の段階で対応予定)。

**既存の判定への影響**: この記録機能が仮に一時的に動かなくなったとしても、
買い候補判定・売却判定・保有判断・利益確定判定やLINE通知には一切影響しません
(記録に失敗した場合は裏側のログにのみ記録され、既存の通知が止まったり
遅れたりすることはありません)。今回の段階ではLINE通知の内容・頻度にも
変更はありません。

**記録は一度確定したら書き換わらない(2026-08再レビュー対応)**: DecisionSnapshotは
「insert-only」、つまり一度保存された記録は後から絶対に上書きされません。
同じ判定の保存処理が(バッチの再実行等で)偶然もう一度走った場合、記録内容が
完全に同一であれば何もせず正常に処理を終えます。万一、同じ判定のはずなのに
記録内容が食い違う異常なケースを検知した場合は、既存の記録をそのまま正として
保持し(新しい値で上書きしない)、裏側のログにのみ記録します。この場合も
既存の買い候補判定・売却判定・保有判断・利益確定判定やLINE通知には一切
影響しません。

**記録の単位(多重度)**: 1件の判定(Recommendation)につき、DecisionSnapshotは
常に1件のみ記録されます(1 Recommendation = 1 DecisionSnapshot)。生産コードを
横断調査した結果、1つの判定が複数の判定種別(買い候補・売却・保有判断・
利益確定)にまたがって記録されることは無いことを確認済みです。

### 12.6 過去バリュエーション比較スコア(Phase B第一弾、2026-08追加・同月3回のコードレビュー対応で仕様確定)

**目的**: 12.5節の自己評価基盤(Phase A)に続き、実際にスコアを計算して記録する
段階(Phase B)を開始しました。第一弾として、「今の株価が、その銘柄自身の
過去の株価水準(PER・PBR)と比べて割安か割高か」を数値化した過去バリュエーション
比較スコアを追加しています。

**スコアの仕様**: +100(過去と比べて非常に割安)〜-100(過去と比べて非常に
割高)の範囲で、0が過去の中立的な水準にあたります。買い候補・売却・保有判断・
利益確定の各判定が確定するたびに算出し、DecisionSnapshotへ記録します。
同業他社や市場平均との比較は行わず、あくまでその銘柄自身の過去の実績とだけ
比較します。参考として、スコアを次の5段階のカテゴリへ丸めた分類も記録します
(カテゴリは記録専用であり、判定には使いません)。

| カテゴリ | 意味 |
|---|---|
| 過去比で非常に割安 | 過去の水準と比べて明確に割安 |
| 過去比で割安 | やや割安 |
| 過去比で標準的 | 過去の中立的な水準に近い |
| 過去比で割高 | やや割高 |
| 過去比で非常に割高 | 過去の水準と比べて明確に割高 |

**現在の株価との比較基準を過去の実績と揃えています**: PER・PBRの算出には
「予想EPSに基づく比率」と「実際に確定した決算実績に基づく比率」という2種類の
考え方があります。過去の水準はデータ提供元から取得できる実際の決算実績
(既に確定した数値)に基づいているため、現在のPERも同じ「実績ベース」の値を
使って比較します(予想ベースの値と実績ベースの値を単純比較すると、算出方法の
違いにより見かけ上の割安・割高が生じてしまうため)。両者の基準が異なると
判断される場合は、その指標を無理に比較せず「未評価」のまま記録します。

**データ品質の確認**: 過去の実績データについて、明らかに異常な値(取得元の
不具合等による極端な数値)は自動的に除外したうえでスコアを計算します。
未来日付のデータ(将来のバックテスト機能で過去時点を再現評価する際に、
本来その時点でまだ存在しないはずのデータを誤って使わないようにするための
安全策)、および評価対象の銘柄と一致しないデータも同様に除外します。除外を
行った場合は、その理由を記録に残します。過去のPER・PBRデータが少ない銘柄
(データ提供元から取得できる実績が実質数年分程度しかない銘柄)については、
無理に点数化せず「未評価」のまま記録します。現在のPER・PBR自体についても、
過去データと同じ「明らかに異常な値」の基準を適用するようにしており、現在の
株価水準が異常値とみなされる場合は、その指標を無理に点数化せず除外します
(PER・PBRの片方のみが異常な場合は、もう片方だけで評価を継続します)。

**データが「その時点で実際に使えたか」の確認(時点整合性)**: 過去の実績データ
には「どの決算期間のものか」という情報のほかに、「実際にいつ利用可能になった
データか」という情報も別に記録しており、評価する時点より後に利用可能になった
データは、たとえ対象の決算期間自体が過去のものであっても使用しません(将来の
バックテスト機能で過去のある時点を再現評価する際、その時点ではまだ公表されて
いなかった決算数値を誤って使ってしまうことを防ぐための安全策です)。実際の
公表日時をデータ提供元から取得できない場合は、少なくとも「このデータを取得
した日時」を保守的な基準として使い、対象の決算期間の末日をそのまま代用する
ことはしません(公表時点を推測で補うと、実際より高精度に見える誤った結果に
なりかねないため)。この結果、評価に使える過去データが少なすぎる状態になった
場合は、無理に評価せず「未評価」のまま記録します。

**決算期末日と、実際にPER・PBR算出に使った株価の時点の一致**: 過去の各決算期
時点のPER・PBRを算出する際に使う株価は、その決算期末日と同じ日、または
それより前で最も新しい取引日の終値のみを使用します(決算期末日より後の株価
を使うことはありません)。決算期末日が土日等の非営業日にあたる場合は、直前の
営業日の終値を使います。株価データが決算期末日から遡って一定期間(14日間)
以内に見つからない場合は、その期のPER・PBRは算出しません(未来側の株価で
補完することもありません)。あわせて、「実際にいつ利用可能になったデータか」
を表す日時は、必ず具体的な日時(タイムゾーン情報を含む値)として記録される
仕組みとし、この情報が欠けたデータが誤って評価に使われることのないようにして
います。

**記録される付随情報**: スコア本体に加えて、「どの程度自信を持てる評価か」
(高い・中程度・低い、または評価不能)、「PER・PBRのうちどちらがどれだけ
評価に使えたか」(カバレッジ)、算出に使った過去データの件数・除外理由も
あわせて記録します。これにより、後から「なぜこの点数になったか」を確認
できます。

**PBRの精度に関する既知の制約と、信頼度への反映**: 過去のPBR算出には、
各決算期時点の実際の発行済株式数の履歴をデータ提供元から安定して取得できない
という制約があり、現在の発行済株式数で近似しています(自己株買い・増資等で
株式数が変動している銘柄では、この近似により誤差が生じます)。この近似が
実際にスコア計算へ使われた場合、その旨を記録に残したうえで、「どの程度自信を
持てる評価か」が最も高い区分(高い)には到達しないようにしています(他の
条件がどれだけ揃っていても、PBR側が近似データに基づく限り中程度が上限に
なります)。

**現時点でできること・できないこと**: この段階では、このスコアは記録される
だけで、買い候補判定・保有判断スコア・売却判定・利益確定判定・LINE通知の
いずれにも一切使われません(12.5節の「Shadow計測」の考え方をそのまま踏襲)。
将来、このスコアが実際に判定の精度向上に役立つかどうかを検証したうえで、
役立つと判断された場合にのみ、判定への組み込みを別の段階で検討します。
株式分割・特別要因(減損等)による一時的な数値の歪みは、データ提供元から
確実に検知する手段が無いため、この段階では個別の検知は行っていません
(明らかな異常値のみ自動除外の対象になります)。

**既存の判定への影響**: 買い候補判定・売却判定・保有判断・利益確定判定の
ロジック自体、およびLINE通知の内容・頻度は一切変更していません。

### 12.7 モメンタムベースのエントリータイミングスコア(Phase B第二弾、2026-08追加、同月3回のコードレビュー対応でv2→v3→v4へ再設計)

**目的**: 12.6節の過去バリュエーション比較スコア(「割安か割高か」)に続き、
「今が技術的に入りやすいタイミングか」を数値化したタイミングスコアを追加
しました。既に計算済みのモメンタム・トレンド情報(6.5節・9節、移動平均・
RSI・MACD・出来高・直近高値からの下落率)を基に算出します。

**重要: このスコアは「モメンタムが強いほど高得点」ではありません。**
初版(v1)は結果的に「モメンタムが強いほど高得点」になってしまっていた
(相場の強弱を示す指標が高いほど加点、直近高値ぴったりが最高点、強い上昇
トレンドが常に最高評価、という設計だった)ため、コードレビューを経て
v2として再設計しました。v2が実際に評価するのは、**「上昇トレンドを維持
しながら、過熱しておらず、エントリーしやすい価格位置にあるか」**です。
具体的には次のような値を高く評価しません。

- 相場の強弱を示す指標(RSI)が極端に高いことを無条件に加点しない
  (45〜60程度の範囲を最も高く評価し、70を超えると過熱として明確に
  減点します)。
- 直近高値にぴったり近いことを最高評価としない(高値からある程度
  (目安3〜8%程度)下がった「適度な押し目」の方を高く評価します)。
- 「適度な押し目」は、上昇トレンドを維持している場合にのみ加点対象と
  します。下降トレンド中に株価が下がっていても、それを「押し目」とは
  評価しません(「高値から下がった」ことと「押し目」であることを混同
  しません)。
- 移動平均線から大きく上方に乖離している状態(過熱)、または大きく
  下方に乖離している状態(トレンド崩れ)のいずれも高く評価しません。
- 「適度な押し目」「移動平均線からやや上に乖離(まだ許容範囲)」
  「直近高値に近い」といった、価格の位置だけで加点になりうる区分は
  すべて、上昇トレンドを維持している場合にのみ加点対象とします
  (2回目のコードレビュー対応(v3)で、一部の区分にしか適用されて
  いなかったこの条件をすべての加点区分へ拡張しました)。下降トレンド
  中は、価格が高値に近い・移動平均線付近にあるといった位置関係
  だけでは加点しません。

**スコアの仕様**: +100(技術的に強い追い風=エントリーに適した状態)〜
-100(技術的に強い逆風)の範囲で、0が中立です。買い候補・売却・保有判断・
利益確定の各判定が確定するたびに算出し、DecisionSnapshotへ記録します。
参考として、スコアを次の5段階のカテゴリへ丸めた分類も記録します(カテゴリ
は記録専用であり、判定には使いません)。

| カテゴリ | 意味 |
|---|---|
| 強い追い風 | エントリー条件が明確に良好 |
| 追い風 | やや良好 |
| 中立 | 中立的な状態 |
| 逆風 | やや不利 |
| 強い逆風 | エントリー条件が明確に不利(過熱・トレンド崩れ等) |

**算出に使う要素**: トレンドの質(株価と移動平均線の並び・傾きから、
相場の強弱を示す指標を使わずに算出。既存のトレンド分類ロジックは相場の
強弱を示す指標を強いトレンドの判定条件に使っているため、二重に評価しない
よう別々に算出します)、20日・60日移動平均線からの乖離(乖離の方向
(上/下)によって評価を変え、単純な乖離幅の大小だけでは評価しません)、
RSI(過熱・エントリー適性のみを評価)、MACD(短期・長期のトレンドの勢いを
示す指標、符号のみ)、直近高値からの下落率(適度な押し目かどうか)、出来高
(単純に多いほど加点はしません)の7要素を、それぞれ設定ファイルの重みで
合成した「基本点」をまず算出します。取得できない要素は無理に推測で補わず、
欠損した要素は0点として加算せず、利用可能な要素の重みだけで正規化します。

**短期急騰・過熱ペナルティは「基本点からの減点」として扱います
(2回目のコードレビュー対応でv3へ再設計)**: 直近5営業日の急騰・相場の
強弱を示す指標の極端な高さ・高値圏の3条件が同時に成立した場合にのみ、
基本点から一定の点数を差し引いて最終点を算出します。過去のバージョン
(v2)では、このペナルティも他の7要素と同じ「加重平均の1要素」として
扱っていたため、過熱情報自体が取得できない場合に「その要素だけ加重平均
から除外される」ことで、かえってスコアが押し上げられてしまう(データが
欠けているほうが有利になる)という問題がありました。v3では、過熱情報が
取得できない場合は単に減点を適用しない(基本点をそのまま最終点とする)
方式に改め、**過熱情報の欠損によって最終点が基本点より高くなることは
ありません**。また、過熱情報が確認できない場合は、「今が過熱していない
とは確認できない」ことを踏まえ、この評価の自信度(下記)が「高い」まで
は到達しない(「中程度」が上限)ようにしています。

**TOPIX・業種指数との相対的な強さは対象外**: 過去のバージョン(v1)には
TOPIX・業種指数との相対的な値動きの強さも含まれていましたが、これらは
「銘柄自身のエントリータイミング」ではなく市場全体・業種全体の環境を
表す情報であるため、将来別途検討する市場・業種環境スコアとの重複評価を
避けるため、本スコアの算出対象から除外しました(参考情報としての記録
自体は引き続き行っています)。

**データ不足時の扱い**: 算出に使えた要素の割合(カバレッジ)が一定の
基準を下回る場合は、無理にスコア化せず「未評価」のまま記録します。トレンド
の質を算出するための移動平均線・傾きが計算できない場合も、無理な既定値
(中立扱い)を使わず、その要素自体を「算出不可」として扱い、カバレッジの
計算対象からも除外します。

**現在値と過去の値動きデータの時点整合性**(2回目のコードレビュー対応で
v3へ追加): 最新の株価(現在値)と、移動平均線・RSI・直近1営業日/5営業日
騰落率などの計算に使う日々の値動きデータは、データ取得の都合上、別々の
タイミングで取得したものであり、必ず同じ日付を指しているとはコード上
保証されていません(通常は一致しますが、休日・取引時間外・データ取得元
の遅延等により、ずれる可能性があります)。ずれを検知した場合、直近1営業日
/5営業日騰落率(短期急騰・過熱ペナルティの判定材料の一部)は実際の値を
使わず「算出不可」として扱い、無理な計算はしません(データが取得できない
ときと同様、捏造せずに「未評価」寄りに倒す設計方針を踏襲しています)。

**現在値より未来の日付を持つ値動きデータは、全ての算出要素から除外します**
(3回目のコードレビュー対応でv4へ追加): 上記の時点整合性チェックは当初
「現在値より未来の値動きデータが混ざっていた場合、直近1営業日/5営業日
騰落率だけを算出不可にする」という設計でしたが、これでは移動平均線・RSI・
MACD・直近高値からの下落率・出来高比率・TOPIX/業種指数との相対的な強さ
(参考記録のみ、算出対象外)といった**他の全ての算出要素**に、まだ確定
していない未来の値動きが混ざってしまう可能性がありました(将来の情報を
使って現在時点の評価をしてしまう「先読み」の一種であり、望ましくありません)。
v4では、現在値の日付より後の値動きデータは、これらの算出要素を含む
全ての計算から内部的に除外するようにしました。現在値自体は実際に観測
された値であり、未来データの有無によって書き換える・補正することは
ありません。なお、未来データを除外した結果、残りのデータの最新日が
現在値の日付とちょうど一致する場合は、直近1営業日/5営業日騰落率も正しく
算出します(未来データが混ざっていたこと自体を理由に、無条件で算出不可
にするわけではありません)。除外が発生したかどうかは、時点整合性の有無
(上記)とは別の情報として記録され、後から「未来データが混ざっていて
除外した」のか「単に値動きデータが現在値より古いだけ」なのかを区別
できます。

過去の値動きデータがどの程度古くても許容するかという上限は、現時点では
設けていません(値動きデータが現在値より古い場合、時点整合性チェックに
よって直近1営業日/5営業日騰落率の算出・過熱判定は行われず、この評価の
自信度も「高い」までは到達しませんが、移動平均線・RSIなど他の算出要素
自体は古いデータのままでも計算されます)。これは現時点での既知の制約です。

**記録される付随情報**: スコア本体(最終点)に加えて、「どの程度自信を
持てる評価か」(高い・中程度・低い、または評価不能)、要素ごとの内訳
(トレンドの質・移動平均線乖離・RSI・MACD・下落率・出来高それぞれの点数)、
短期急騰・過熱ペナルティを差し引く前の基本点、過熱ペナルティが発動したか
どうかと実際に差し引いた点数、および元になった生の指標値(RSI・下落率・
出来高比率・直近1営業日/5営業日の騰落率・現在値と過去データの時点整合性
の有無・未来データを除外したかどうか等)もあわせて記録します。これにより、
後から「なぜこの点数になったか」「どの要素が実際に有効だったか」「過熱
ペナルティが影響したか」「未来データの除外が発生していたか」を確認
できます。カテゴリ分類に使った閾値自体も、判定当時の設定値として記録
します(閾値が改定された場合でも、過去の記録がどの基準で分類されたかを
後から特定できるようにするため)。

**現時点でできること・できないこと**: 12.6節の過去バリュエーション比較
スコアと同様、この段階ではスコアは記録されるだけで、買い候補判定・保有判断
スコア・売却判定・利益確定判定・LINE通知のいずれにも一切使われません
(12.5節の「Shadow計測」の考え方を踏襲)。各要素の重み・区分の境界値は
現時点では仮説段階の初期値であり、今後実際の判定結果の振り返り
(DecisionSnapshotの成績集計)を踏まえて調整していく想定です。将来、この
スコアが実際に判定の精度向上に役立つかどうかを検証したうえで、役立つと
判断された場合にのみ、判定への組み込みを別の段階で検討します。なお、
実際の過去時点で入手可能だったデータのみを使って「その時点で何点だったか」
を過去に遡って完全に再現できることまでは、現時点では検証・保証していません
(既知の制約であり、安全と断定しているわけではありません)。今回(v4)保証
している範囲は、あくまで「現在値の日付より未来の値動きデータが入力に
混ざっていても、その未来データを算出要素に使用しない」ことのみであり、
「完全に過去再現可能(backtest safe)になった」という意味ではありません。

**既存の判定への影響**: 買い候補判定・売却判定・保有判断・利益確定判定の
ロジック自体、モメンタム・トレンド情報自体の既存の算出方法(トレンド分類
ロジック自体は無変更)、およびLINE通知の内容・頻度は一切変更していません。

### 12.8 決算サプライズスコア(Phase C、2026-08追加、同月のコードレビュー対応でv2・v3へ再設計、3回目のコードレビュー対応で外部データ取得の抑止・監査項目を追加)

**目的**: 「直近の決算が、事前の期待に対して良かったか悪かったか」を
-100(強い悪材料サプライズ)〜+100(強い好材料サプライズ)で数値化した
スコアです。12.6節・12.7節のスコアとは異なる評価軸で、決算そのものの
中身を評価します。

**実装前の調査で判明した制約**: このスコアは当初、(1)実績が事前の
アナリスト予想をどれだけ上回った/下回ったか、(2)今回の決算の進捗が
その企業の過去数年分の同時期平均と比べてどうか、(3)会社自身の業績
予想が上方修正・下方修正されたか、(4)配当予想が増額・減額されたか、
という4種類の要素での構成を検討しましたが、実装に着手する前に取得
可能性を調査した結果、(2)と(3)は現在利用しているデータ提供元では
実現できないと判断しました。

- (2)については、今回の四半期の進捗率を「その企業の過去3〜5年分の同じ
  時期の平均」と比較する設計でしたが、無償で取得できる四半期実績は
  直近5四半期分(1年強)にとどまり、3〜5年分の比較に必要なデータ量が
  根本的に不足していたため、この要素は見送りました。
- (3)については、業績予想の修正に関する開示情報自体が、日本の適時開示
  制度(TDnet)専用で公開されており、本システムが利用している開示情報
  取得経路(EDINET臨時報告書)では構造的に取得できないことが判明した
  ため、この要素も見送りました。

**「配当予想の増額/減額」も対象外としました(コードレビュー対応でv2へ
変更)**: 初版(v1)では上記(4)も要素として含めていましたが、この判定に
使う既存データ(6.3節の減配判定ロジック)は「前年度に実際に確定した年間
配当実績」と「現在の年間予想配当」を比較したものであり、「今回の決算に
おいて配当予想が上方修正/下方修正されたか」という意味のデータではない
ことが判明しました。意味の異なるデータを「今回決算のサプライズ」として
扱うのは不適切なため、この要素は決算サプライズスコアから除外しました
(配当の増額・減額の傾向としての評価は、12.9節の業績トレンドスコアの
「配当方向」として引き続き行っています。こちらは「配当の方向性」を見る
評価であり、意味が整合しています)。

**実際に使う要素(v2)**: 上記の調査結果を踏まえ、取得できない、または
意味が異なるデータを無理に代替せず、確実に取得・検証できる以下の1要素
のみでスコアを構成します。

- **アナリストコンセンサスとの乖離**: 直近で確定した決算の実績EPSが、
  Yahoo Financeの決算サプライズ履歴が返すEPS予想値をどれだけ上回った/
  下回ったかを評価します(コードレビュー対応v3: この予想値が「決算発表
  直前時点で実際に市場が参照していたコンセンサス」であったことを独立に
  検証できるタイムスタンプ証跡は、無償データからは取得できません。その
  ため断定的な表現は避け、「Yahoo Financeが返す予想値」という取得元に
  忠実な表現にしています)。極端に高い/低い上振れ・下振れほど強く評価し、
  小さな乖離は中立的に扱います。この要素は、大型株・中型株では概ね
  取得できますが、アナリストによる予想自体が存在しない小型株では算出
  できません。その場合、他のデータ(配当など)で穴埋めすることはせず、
  このスコア自体を「算出不可」として記録します(意味の異なるデータで
  無理にスコアを作らない、という方針を徹底しています)。

**決算がまだ財務データへ反映されていない期間は評価しません**: 決算予定日
を経過したにもかかわらず無償データで発表実績を確認できない期間(12.7節
より前に導入済みの「決算発表確認待ち」の仕組みと同じ判定)は、古い決算
データを最新として扱わないよう、このスコア自体を算出せず記録します
(「評価対象外」として区別して記録します)。

**「評価対象外」になると分かっている場合、外部データ取得を省略します
(3回目のコードレビュー対応で追加)**: 上記の「評価対象外」になることが
呼び出し前から確定している場合(下記の「古すぎる決算予定日」判定で
関連性ありと判定された場合)、この銘柄についてYahoo Financeへの実績・
予想EPS問い合わせを行わないようにしました。判定結果自体(評価対象外に
なること)は変わらず、システムの応答速度・外部データ取得元への負荷軽減
のみを目的とした最適化です。それ以外のケース(通常評価・古すぎる決算
予定日で評価継続する場合)では、従来どおり毎回問い合わせを行います。

**古すぎる決算予定日で評価停止が無期限に続かないようにします(コードレビュー
対応でv3へ追加)**: データ提供元が何か月も前の過去の決算予定日を更新せず
返し続けるケースでは、上記の「評価しません」判定が無期限に継続してしまう
おそれがあります。これを防ぐため、利益確定判定(6.6節)が既に使っている
「決算予定日の関連性」判定の仕組みをこのスコアでも再利用しました。決算
予定日からの経過日数が一定の範囲内であれば引き続き「評価対象外」とします
が、それを超えて経過し、かつ財務データの更新も確認できない場合は、決算
待ちを理由にした評価停止をやめ、現在取得できている最新の確定データで
Shadow計測を継続します(関連性が「不明」であることを悪材料として減点する
ことはありません)。どちらの判定を使ったかは監査情報として記録します。

**現時点でできること・できないこと**: このスコアに使う実績値・アナリスト
予想値は、判定を行った時点で取得・保存した値をその後の答え合わせ
(DecisionSnapshotの成績集計)に使うことは想定していますが、過去の
特定の評価日を指定してこの値を再現する(いわゆるバックテスト)ことは
できません(データ提供元が「現在から見た最新の値」しか提供しないため)。
このスコアは記録されるだけで、買い候補判定・保有判断スコア・売却判定・
利益確定判定・LINE通知のいずれにも一切使われません(12.5節の「Shadow
計測」の考え方を踏襲)。

**判定当時の入力値を監査情報として保存します(コードレビュー対応でv2・v3へ
追加)**: 上記のとおり過去の評価日を指定した再現(バックテスト)は
できないため、代わりに「判定当時に実際に何を見てこの点数になったか」を
後から確認できるよう、突合した決算期(四半期末日)・実績EPS・コンセンサス
予想EPS・データの取得元・取得日時・決算反映確認の状態・上記の決算予定日
関連性判定の結果を、スコア本体とあわせて記録するようにしました。

**既存の判定への影響**: 買い候補判定・売却判定・保有判断・利益確定判定の
ロジック自体、既存の決算日検証・配当データの算出方法、およびLINE通知の
内容・頻度は一切変更していません。

### 12.9 業績トレンドスコア(Phase C、2026-08追加、同月のコードレビュー対応でv2・v3へ再設計、3回目のコードレビュー対応で監査項目を追加)

**目的**: 12.8節の決算サプライズスコアが「直近1回の決算が良かったか」を
見るのに対し、こちらは「複数四半期にわたって業績が改善傾向にあるか、
悪化傾向にあるか」を-100(強い悪化トレンド)〜+100(強い改善トレンド)
で評価する、完全に独立した評価軸です。

**実際に使う要素**: 実装前の調査の結果、以下の3要素(+補助的な1要素)で
構成します。いずれも「前の期と比べてどれだけ増減したか」という変化の
方向・度合いのみを評価対象とし、営業利益や営業キャッシュフローの
絶対水準(規模)自体を独立した評価要素としては持っていません(会社の
規模による有利・不利が生じないようにするための設計です)。売上高・1株
当たり利益(EPS)の推移、および利益率の改善度合いは、現在のデータ取得
方法では四半期ごとの値を取得していないため、今回は対象外としています
(将来、データ取得方法自体を拡張すれば対応可能になる見込みです)。

- **営業利益トレンド**: 直近四半期の営業利益が、その前の四半期と比べて
  どれだけ増減したかを評価します。
- **営業キャッシュフロートレンド**: 同様に、営業キャッシュフローの
  直近四半期の増減を評価します。
- **配当方向**: 配当据え置き・増配・減配の判定結果(6.3節)を再利用し、
  配当の方向性として評価します(12.8節のアナリストコンセンサス乖離とは
  独立した重み付けで評価します)。
- **(補助的な)勢いの変化**: 上記の営業利益トレンドが、加速しているか
  減速しているかを追加で評価します。直近5四半期程度という限られた
  データ量でしか算出できないため、他の要素より低い重みを持つ補助的な
  位置づけです。

**赤字企業・営業キャッシュフローがマイナスの企業でも改善/悪化の方向を
正しく評価します(コードレビュー対応でv2へ修正)**: 初版(v1)では、
前期比の変化率の計算方法に不具合があり、営業利益や営業キャッシュフローが
マイナス(赤字・資金流出)の企業で、実際には改善しているのに「悪化」と
誤判定される(またはその逆)ケースがありました。v2では、赤字が縮小した
場合を「改善」、赤字が拡大した場合を「悪化」、赤字から黒字へ転換した
場合を「強い改善」、黒字から赤字へ転落した場合を「強い悪化」と、直感に
沿った方向で正しく評価するよう修正しました。前期の値がちょうど0の場合
(0を挟んだ変化のため通常のパーセント計算ができない)は、パーセントを
使わず今期の値が黒字か赤字かに応じて明示的に評価します(推測で極端な
数値を作りません)。あわせて、赤字/黒字が入れ替わるような大きな変化を
挟んだ「勢いの変化」(上記補助要素)は、比較の前提が崩れるため無理に
算出せず「算出不可」として扱うようにしました。

**四半期実績が取得できず年次決算にとどまる銘柄は、信頼度を一段階
下げます(コードレビュー対応でv2へ追加)**: 財務データの取得元によっては、
四半期ごとの実績が取得できず、年に一度の本決算データしか得られない
銘柄があります(既存の財務データ取得ロジックが自動的に判別しています)。
この場合、営業利益・営業キャッシュフローのトレンド自体は年次データを
使って算出しますが(「誤ったデータ」として除外はしません)、四半期
ごとの情報より粒度が粗いことを踏まえ、この評価の自信度は「高い」までは
到達しない(「中程度」が上限)ようにしました。四半期実績・年次データの
いずれも取得できない銘柄については、営業利益・営業キャッシュフロー・
勢いの変化のいずれも算出せず「算出不可」として扱います(この場合も
配当方向だけで無理に高い自信度にはしません)。

**決算がまだ財務データへ反映されていない期間は評価しません**: 12.8節と
同じ理由・同じ判定条件で、この期間は「評価対象外」として記録します。
古すぎる決算予定日で評価停止が無期限に続かないようにする仕組み
(コードレビュー対応でv3へ追加)も12.8節と全く同じものを使います。

**判定当時の入力値を監査情報として保存します(コードレビュー対応でv2・v3・
3回目の対応で拡充)**: 各成分の算出に使った直近・その前の四半期実績値、
前期比変化率、四半期実績由来か年次決算由来かの区分、決算予定日関連性判定の
結果を、スコア本体とあわせて記録するようにしました。あわせて(v3)、各
成分の値が「どの決算期(四半期末日)の値なのか」、四半期実績由来(TTM)か
年次決算フォールバック由来(ANNUAL)かの種別も、値そのものと組にして記録
するようにしました(値だけでは「今期と前期のどちらの値か」「四半期実績と
年次決算のどちらの粒度か」が後から復元できなかったための改善です)。3回目の
コードレビュー対応では、「評価対象外」判定に使ったもう一方の入力(決算発表
確認待ちの状態)も、決算サプライズスコアと同様に監査情報として追加保存する
ようにしました(判定条件・スコア自体は変更していません)。

**現時点でできること・できないこと**: このスコアも記録されるだけで、
買い候補判定・保有判断スコア・売却判定・利益確定判定・LINE通知の
いずれにも一切使われません(12.5節の「Shadow計測」の考え方を踏襲)。

**既存の判定への影響**: 買い候補判定・売却判定・保有判断・利益確定判定の
ロジック自体、既存の決算日検証・配当データの算出方法、およびLINE通知の
内容・頻度は一切変更していません。

### 12.10 判定の振り返り分析の強化(2026-08追加)

**目的**: 12.5節で記録が始まったDecisionSnapshot(判定確定時の記録)を、
12.6〜12.9節で計算されるようになった各スコア(過去バリュエーション比較・
タイミング・決算サプライズ・業績トレンド)の観点別に集計・比較できるように
しました。`jstock decision-performance segments`コマンドで、1つのスコアを
「カテゴリ別」「信頼度別」「データの充実度(カバレッジ)別」「計算方式の
バージョン別」に分けた成功率・平均リターン等を確認でき、`jstock
decision-performance compare`コマンドで、スコアの数値範囲を2グループに
分けて成績を比較できます。

**過去の記録はその時点の基準で解釈します**: カテゴリ・信頼度・データの
充実度の判定は、現在読み込まれている設定やカテゴリの定義ではなく、
DecisionSnapshotに保存された「判定当時に実際に使用した設定値」だけを
使って行います。将来カテゴリの区分名が変わっても、過去の記録がその
変更によって分析対象から漏れることはありません。

**壊れたデータが1件あっても、レポート全体は止まりません**: 過去のごく
一部の記録で保存データに想定外の不備(欠損・型違いなど)があっても、
その記録は該当する分析軸(たとえばデータの充実度別の集計)からのみ
除外され、他の分析軸(カテゴリ別・信頼度別など)や他の記録の集計は
そのまま継続します(裏側のログにのみ記録が残ります)。

**既存の判定への影響**: この分析機能はDecisionSnapshotを読み取るだけの
手動実行コマンドであり、買い候補判定・売却判定・保有判断・利益確定判定の
ロジック自体、LINE通知の内容・頻度には一切影響しません。

### 12.11 目安買付価格帯・利確価格帯の記録(2026-08追加)

**目的**: 12.6〜12.9節の各スコアに続き、「実際にいくらで買う・売ると
良さそうか」の目安を、適正価格レンジ(既存の3手法統合適正価格)を基準に
算出し、DecisionSnapshotへ記録する仕組みを追加しました。**この目安は
記録されるだけで、実際の買付価格提案(entry_buy_price等の既存3段階買付
価格)・売却価格提案(既存sell_prices)・買い候補判定・保有判断スコア・
売却判定・利益確定判定・LINE通知のいずれにも一切使われません**(12.5節の
「Shadow計測」の考え方を踏襲する、独立した記録専用の目安です)。

**目安買付価格帯(4段階)**: 適正価格レンジの中立値を上限とし、そこから
信頼度別の余裕幅(打診買い〜本格買いへ向けて余裕幅が広がる4段階)を
差し引いた4つの価格の目安を算出します。銘柄自身の過去バリュエーション
水準(12.6節)が「割安」寄りであれば余裕幅をやや縮め、「割高」寄りで
あれば余裕幅をやや広げます。技術的タイミングスコア(12.7節)が「追い風」
であれば「本命買い」の目安価格を現在値方向へ、「向かい風」であれば
移動平均線方向(より安い側)へ寄せます。どの調整を行っても、4段階の
価格が「本格買い目安 ≦ 本命買い目安 ≦ 打診買い目安 ≦ 上限」の順序を
崩すことはなく、上限(適正価格レンジの中立値)を超える価格が算出される
こともありません。あわせて、適正価格レンジの弱気シナリオ値を「前提を
見直すべき参考価格」として記録します(損切りラインという意味ではあり
ません)。必要なデータ(適正価格レンジ・過去バリュエーション比較スコア・
タイミングスコア・移動平均線)が十分に揃わない場合は、無理に算出せず
「算出不可」として記録します。

**目安利確価格帯(保有銘柄のみ)**: 適正価格レンジの中立値・強気値を基準に、
一部利確を検討し始める価格帯(中立値付近の狭い範囲)と、強気シナリオ
まで伸びた場合の利確目安を算出します。銘柄自身の過去バリュエーション
水準・タイミングスコアによる調整は目安買付価格帯と同じ考え方です。
これとは別に、実際の取得単価を基準にした2つの参考ライン(含み損が
一定割合に達した場合の見直しライン、含み益が一定割合に達した場合の
見直しライン)もあわせて記録しますが、この2ラインは取得単価が変わった
場合にのみ変化し、適正価格レンジを基準にした利確価格帯には一切影響しません。
必要なデータ(適正価格レンジの中立値・強気値の両方)が十分に揃わない
場合は、目安買付価格帯と同様、5つの価格すべてを「算出不可」として記録し
(取得単価だけから計算できる2ラインだけを部分的に記録することはしません)、
一部の目安だけが宙に浮いた状態を防ぎます。

**既存の判定への影響**: 買い候補判定・保有判断スコア・売却判定・
利益確定判定のロジック自体(既存の3段階買付価格・売却価格提案を含む)、
適正価格レンジそのものの計算方法、LINE通知の内容・頻度は一切変更して
いません。

### 12.12 市場全体・所属セクターの地合いスコアの記録(Phase D、2026-08追加)

**目的**: 12.6〜12.11節までの各スコアは、いずれも銘柄自身のデータ(過去
バリュエーション・値動き・決算内容・適正価格レンジ)から算出しています。
これに対しPhase Dでは、「企業自体は魅力的でも、市場全体または所属
セクターが強い逆風なのか」という、銘柄自身では捉えられない外部環境の
観点を、独立した記録専用のスコアとして追加しました。**この記録も
12.5節のShadow計測の考え方を踏襲しており、買い候補判定・保有判断
スコア・売却判定・利益確定判定・目安買付価格帯/利確価格帯・LINE通知の
いずれにも一切使われません**。

**市場全体の地合いスコア**: TOPIXの値動きのみを使い、トレンドの構造
(移動平均線の位置関係と傾き)・直近1〜3か月程度の値動き・直近高値からの
下落度合いの3つの観点を組み合わせ、-100(非常に強い逆風)〜+100(非常に
強い追い風)の点数で表します。「市場が今後上がる/下がるという予言」では
なく、あくまで評価時点での地合いの質を表す点数です。

**所属セクターの地合いスコア**: あらかじめ業種とセクターETF(上場投資
信託)を対応付けた設定がある業種のみ算出します。市場全体の地合いスコア
と同じ観点に加え、「市場全体と比べてこのセクターがどれだけ強い/弱いか」
という相対的な強さを主要な観点として組み合わせます(市場全体が+10%上昇
していてもセクターが+2%しか上昇していなければ、相対的には弱いという
評価になります)。

**「対象外」と「今回は算出不可」の区別(コードレビュー対応)**: 所属
セクターの地合いスコアには、記録上2種類の「評価していない」状態があり、
明確に区別しています。(1)**対象外**: そもそもその業種に対応する
セクターETFの設定が無い場合。業種自体がこの評価の対象外であることを
表します。(2)**今回は算出不可**: 対応するセクターETFの設定はあるが、
値動きデータが取得できない・データが少なすぎる等の理由で、その時点
だけたまたま算出できなかった場合。業種自体は評価対象であり、次回以降は
算出できる可能性があります。この2つを混同すると、「その業種は評価対象
外」なのか「今回はデータの都合でたまたま評価できなかった」なのかが
後から区別できなくなるため、別々の状態として記録しています。

**統合スコア**: 市場全体のスコアを軸とし、所属セクターのスコアが算出
できた場合は両者を組み合わせた点数を、算出できなかった場合は市場全体の
スコアのみをそのまま採用します(セクターのスコアを0点として混ぜること
はありません)。セクターのスコアが無い場合は、情報が市場全体分しか無い
ことを踏まえ、この統合スコアの「どの程度自信を持てる評価か」の上限を
一段階下げます。統合スコア自身にも「どの程度データが充実しているか」の
最低基準があり、市場・セクター双方から合成したデータの充実度がこの
基準を下回る場合は、統合スコア自体を「算出不可」として記録します
(市場全体・所属セクターの各スコアがそれぞれ「算出不可」の最低基準を
持つのと同じ考え方を、統合スコアにも適用しています)。

**評価できない場合の扱い**: 各スコアの算出に使う個々の観点(トレンド・
値動き・相対的な強さ等)のうち、必要なデータが十分に揃っている観点だけを
使って点数を算出します。必要なデータが不足している観点を0点や中立として
穴埋めすることはありません。全体として必要なデータの充実度が最低基準を
下回る場合は、その銘柄・その時点では「算出不可」として記録します。
トレンドの構造(移動平均線)・値動きの観点についても、あらかじめ設定した
最低限必要なデータ本数(例: 移動平均線なら60営業日分、値動きの長期側
[60日]観点なら61営業日分)を実際に満たしているかを評価可否の条件として
使っています(値動きの短期側[20日]観点は、長期側の本数が不足していても
単独で評価を継続します)。

**評価時点より未来のデータを使わない**: 市場全体・セクターの値動き
データに、評価しようとしている時点より後の日付のデータが混ざっていた
場合は、それを一切使わずに算出します(将来のバックテスト機能で過去の
ある時点を再現評価する際に、その時点でまだ知り得なかった値動きを
誤って使ってしまうことを防ぐため)。

**データ鮮度の判定は暦日ではなく営業日で行う**: 値動きデータの最新日が
評価時点よりどれだけ古いかは、単純な暦日の差ではなく、実際に取引が
行われた営業日の日数で判定します(コードレビュー対応)。例えば金曜日の
データを月曜日に評価する場合、暦日では3日差ですが、間に取引が行われた
営業日は1日のみのため、通常は1営業日分の遅れとして扱われます。年末年始・
ゴールデンウィーク等の連休をまたぐ場合も同様に、実際に開いていた営業日
の本数だけで判定するため、連休の長さによって不必要に「データが古い」と
判定されることはありません。この基準を超えて古いデータの場合でも、
「算出不可」とはせず、代わりに「どの程度自信を持てる評価か」を一段階
下げることで対応します。

**既知の制約(sector_etf_mapが未整備)**: 本書執筆時点では、業種と
セクターETFを対応付ける設定(`momentum_rules.yaml`の`sector_etf_map`)が
空のままであるため、本番運用では所属セクターの地合いスコアは全銘柄で
「対象外」として記録されます。将来、この記録を判定ロジックへ統合するか
どうかを検討する段階になった場合、実際の記録データから有効性を評価する
ためには、事前にこのセクターETF対応付け設定を追加しておく必要があります。

**既存の判定への影響**: 買い候補判定・保有判断スコア・売却判定・
利益確定判定のロジック自体、目安買付価格帯・目安利確価格帯の計算方法、
LINE通知の内容・頻度は一切変更していません。

### 12.13 通知検証モード(2026-08追加)

**目的**: 通知の文面や表示形式を変更したとき、実際に本番のLINE画面で
どう表示されるかを確認したい場合があります。しかし通常運用には
「直近に同じ銘柄へ通知済みなら再送しない」という仕組み(10節)がある
ため、変更後の文面を確認したくても、その日すでに通知済みの銘柄は
再送されず確認できないという問題がありました。これを解消するため、
**本番のAWS環境・本番データ・本番の分析/判定ロジックはそのまま使い
つつ、再送しない仕組みだけを一時的に無効化し、通常運用の履歴を一切
汚さずに実際のLINEへ通知を送って文面を確認できる「検証モード」**を
追加しました。

**対象範囲**: 「買い候補分析」「保有銘柄分析(売却・利確・保有判断
スコア・ポートフォリオ集中リスク・要手動確認)」およびそれらの完了
まとめ通知が対象です。ウォッチリスト自動追加の通知・適時開示の速報
通知・週次/月次/四半期のレビューは対象外です(個別銘柄の売買判断を
直接促す通知ではないため)。

**使い方**: 通常の自動実行(毎日決まった時刻に自動で始まるもの)は
何も変更する必要がなく、これまでどおり動きます。検証モードは、
AWS側の管理画面またはコマンドから、対象の処理を「検証モードで」と
明示して手動で起動した場合のみ動作します。誤って自動実行が検証
モードになってしまうことはありません。

**検証モードで送信される通知の見分け方**: 検証モードで送信された
LINE通知は、必ず本文の冒頭に次の表示が付きます。

```
【🧪 検証モードで送信】
※本通知は通知仕様確認用です。
```

**検証モードでも変わらないこと**: 「本当に通知すべき内容か」の判定
(買い条件を満たしているか、データに問題がないか、業種集中度等の
制限に引っかからないか、通知件数の上限(最大5件)等)は通常運用と
完全に同じ判定を使います。検証モードだからといって、本来なら通知
対象にならない銘柄を無理やり通知することはありません。またデータ
品質に問題があり通常なら「要確認」の通知に切り替わるケースでは、
検証モードでも同じように切り替わります(元の売却・利確通知を強制的に
送ることはしません)。

**検証モードで変わること**: 「直近に同じ内容で通知済みだから今回は
送らない」という再送しない判断だけを無効にします。そのため、検証
モードでは、通常なら再送されないはずの銘柄も含めて通知されます。

**通常運用の記録を汚さない仕組み**: 検証モードで送信した通知は、
通常運用の通知履歴(次回以降の「直近に通知済みか」の判定に使う記録)
には一切残しません。したがって、検証モードを何度実行しても、その後の
通常運用の再送要否の判定には影響しません。また、検証モードでの分析
結果は、通常運用の判定履歴(振り返り分析・過去の判定検証で使う記録、
12節参照)にも残りません。買い候補分析については、複数の処理が
連携して1つの通知にまとめる仕組み上、検証モードの実行中だけ一時的に
専用の作業領域へ記録が残りますが、通知が完了すると自動的に削除され
(万一削除に失敗しても、2時間で自動的に消える安全策があります)、
本番の判定履歴とは物理的に別の場所に隔離されているため混ざることは
ありません。保有銘柄・売買履歴・ウォッチリストといった、利用者の
投資状況そのものを表すデータは、検証モードから一切変更されません。
保有判断スコアが参照する「投資ストーリー維持の基準(baseline、7節)」
「個別購入理由」「監査ログ(13節)」についても、検証モードでは既存の
基準・購入理由が本番にあればそれを読むだけに留め、まだ無い場合は
本番と同じ初回作成ルールで一時的な基準・購入理由をその場で作るだけで
本番へは保存しません。これにより保有判断スコアやLINE通知本文は通常
運用と全く同じロジックで確認できる一方、検証モードを何度実行しても
本番の基準・購入理由・監査ログが増えたり書き換わったりすることは
ありません(2026-08-11コードレビュー対応)。

**既存の判定への影響**: 買い候補判定・保有判断スコア・売却判定・
利益確定判定のロジック自体、目安買付価格帯・目安利確価格帯の計算方法、
通常運用時(検証モードを使わない場合)のLINE通知の内容・頻度・再送
しない仕組みは一切変更していません。

## 14. 用語集

| 用語 | 意味 |
|---|---|
| ウォッチリスト | まだ買っていないが、気になっていて監視したい銘柄のリスト |
| 適正価格(フェアバリュー) | 会社の価値から見積もった「妥当と考えられる株価」の目安。1つの数字ではなく幅(弱気・中立・強気)で表示される |
| 利確(利益確定) | 含み益が出ている株の一部または全部を売って、利益を確定させること |
| 損切り | 損失を確定させてでも、それ以上の損失拡大を防ぐために売ること |
| 含み益・含み損 | まだ売っていない株について、購入時と比べて今どれだけ得(損)しているかの評価額 |
| 総合利回り | 配当利回りに、株主優待の価値も加味した利回り |
| 権利確定日 | この日に株を保有していると、配当や株主優待を受け取る権利が得られる基準日 |
| PER(株価収益率) | 株価が、その会社の1株あたり利益の何倍かを示す指標。割安・割高の目安の一つ |
| PBR(株価純資産倍率) | 株価が、その会社の1株あたり純資産の何倍かを示す指標。割安・割高の目安の一つ |
| 適時開示 | 上場企業が投資家向けに義務として行う公式発表(業績修正・不祥事など) |
| 一次情報 | 会社自身が発表した公式な情報(決算短信・適時開示など)のこと。二次情報(外部サイトの推定値など)より信頼度が高い扱い |
| ルールバージョン | 判定に使う基準(しきい値)のひとまとまりを、変更履歴つきで管理するための単位 |
| 信頼度 | その判定のもとになったデータや計算の確からしさの度合い(高・中・低) |
| DCF(割引キャッシュフロー法) | 会社が将来生み出すお金を、現在の価値に割り引いて企業価値を見積もる計算方法 |
| 保有判断スコア(6.9節) | 企業品質スコア・投資ストーリー維持スコア・リスク控除スコアを1つに合算した点数。「投資した前提が崩れていないか」の新しい判定方式で使う(利益確定の判定には使わない) |
| DecisionSnapshot(12.5節) | 買い候補・売却・保有判断・利益確定の各判定が確定した瞬間の最終判断値(現在値・適正価格レンジ等)を、後から書き換わらない形で記録した控え。判定精度向上機能・自己評価基盤(Phase A)で導入 |
| 目安買付価格帯・目安利確価格帯(12.11節) | 適正価格レンジを基準に算出する、参考用の買付・利確価格の目安。DecisionSnapshotへ記録されるだけで、実際の買付価格提案・売却価格提案・各種判定・LINE通知には一切使われない |
| 市場全体・所属セクターの地合いスコア(12.12節) | TOPIX・セクターETFの値動きから算出する、-100〜+100の外部環境スコア。DecisionSnapshotへ記録されるだけで、各種判定・目安買付価格帯/利確価格帯・LINE通知には一切使われない |

## 15. 現時点でできないこと・既知の制約

正直にお伝えすることを重視しているため、「まだ対応していないこと」を
まとめておきます。

| 項目 | 制約の内容 |
|---|---|
| 買い候補の自動探索範囲 | ウォッチリスト登録銘柄・保有銘柄が対象(2026-07-31改訂。5.6節)。市場全体の自動スキャンは未対応 |
| 買い増し提案の株数 | 常に最低売買単位(1単元)分のみを想定。手元資金にどれだけ余裕があるかのデータが無いため、それ以上の株数・金額は提案しない(5.6節) |
| 買い増し時の業種集中度チェック | 保有銘柄全員分の時価総額がその日のうちにそろわない場合、集中度を「算出不可」として扱い、買い増し候補の通知自体を送らない(時価総額と取得金額を混在させて計算することはしない) |
| 適時開示の取得範囲 | 保有銘柄のみが対象。決算短信(TDnet)そのものは取得できず、EDINET臨時報告書のみ |
| 株主優待の自動取得 | 非対応。必ず手動登録が必要 |
| 業種平均との比較 | PER・PBRはその銘柄自身の過去水準とのみ比較し、同業他社・市場平均との比較は未実装 |
| 簡易DCF | 本来必要な金利・リスクプレミアムのデータが無いため簡略化した計算方法を使用。信頼度は「中」が上限 |
| 業種別の専用評価モデル(銀行・リース業・医薬品・自動車部品など) | 業種の識別まではできるが、業種特有の指標(自己資本比率規制・新薬パイプライン・自動車生産台数への感応度など)を使った専用の評価計算はまだ未実装。該当業種は「高い信頼度」の判定を出さず、必要安全余裕率を加算する対応にとどめている(買い候補判定・保有銘柄判定の両方で共通の方針) |
| 主要顧客への依存度(自動車部品業種) | 個社ごとの取引先集中度データが無いため、業種特性としてAUTOMOTIVE_PARTS区分の銘柄全体に一律で安全余裕率を加算する簡易対応にとどめている |
| 業種(セクター)単位の集中リスク | 個別銘柄1つあたりの比率のみチェック。業種単位のチェックは未実装 |
| 過去の値動きシミュレーション(バックテスト) | 特定の1つのしきい値(最低利回り)のみ対応。かつ、基準を緩める方向の検証はできない(過去に除外された銘柄のデータが残っていないため) |
| 振り返りの総合リターン | 株価の変動分のみを計算。配当・優待を含めた正確な総合リターンは未算出 |
